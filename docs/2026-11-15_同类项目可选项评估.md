## 一、术语小抄（看懂下文够用）

| 术语 | 一句话解释 |
|---|---|
| 分块 | 把大文件切成固定大小的"块"（现在 8 MiB 一块），一块一块传。 |
| 多流 | 同时开几条网络连接一起传，像多开几个收银台。 |
| 哈希 / 指纹 | 给文件内容算一个固定长度的"指纹"，内容变一点，指纹就完全不同。 |
| BLAKE3 | 一种算指纹的算法，速度快、能利用多核。 |
| 位图 | 一张"哪些块已经收到了"的记账表（实际是 `.tcpart.map` 文本文件）。 |
| mtime | 文件的"最后修改时间"。 |
| 协议 | 两台设备之间约定的"说话格式"，改格式就可能影响新旧版本互通。 |
| caps / 能力协商 | 握手时互相报一句"我会哪些新功能"，对方不会就退回老做法。 |
| pack | 一次请求多块，减少来回次数（v0.14 已做）。 |
| fsync | 强制把数据真正写进磁盘，而不只是交给操作系统的缓存。 |
| inode / 文件号 | 文件系统内部给每个文件发的"身份证号"，改名不变、替换会变。 |
| Merkle 树 | 一种分层指纹，可以只验证文件里的某一段，而不必整份重算。 |
| SAF | 安卓的"存储访问框架"，App 通过系统给的句柄读写文件，常常拿不到真实路径。 |
| WifiLock | 一个让 Wi-Fi 网卡别为了省电"睡觉"的开关。 |
| 直接 I/O / 零拷贝 | 跳过系统缓存、直接在磁盘和内存之间搬数据的技术。 |

## 二、逐项评估

### 1. 单文件失败不中断整批

**现在是什么状况**
接收端遇到某个文件写不进去（没权限、磁盘满、文件被占用），或者校验对不上，会立刻结束整场传输；这个文件之后的文件都不会落地。已经传完的文件会保留，未完成的部分留在 `.tcpart`（半成品文件）里。

**改成什么样**
一个文件出错就记下来、跳过它继续传后面的，最后给一张"哪些成功、哪些失败、为什么失败"的清单；失败项可以单独重发。

**解决谁的什么麻烦**
传 10 万个文件（源码树、照片库）时，一个只读文件或一个坏文件名就让整批停下，用户得先找出问题文件、删掉、再整个重来。这是"能不能用"的问题，不是快慢问题。

**能提升多少**
不是速度提升，是成功率。仓库验收文档本来就写着"单文件失败不拖垮整批"（主规划第 41 行、M3 验收第 409 行），但代码实际是"整场失败"，v0.15 设计文档也明写"任一数据流出错整场会话失败"。**这是一处明确的口径冲突。**

**要付出什么代价**
中等。接收端收尾循环、失败清单、历史记录都要改；如果要在传输过程中就告诉发送端"这个文件别传了"，还要加一种新的控制消息，并走能力协商，否则旧版本收到不认识的消息会直接报错。

**风险和副作用**
- 语义要先定清楚：跳过后，这一场算成功还是部分成功？重发时要不要自动只补失败项？
- 与 v0.15"任一流失败整场失败"的设计相反，需要改设计文档，不能只在代码里偷偷改。
- 失败文件留下的半成品如何标记，要避免下次被误当成"可续传"。

**状态**：暂停（原拟随 v0.17，2026-11-15 起全部排期待重估）。
**卡在哪**：原计划 v0.17 先做「失败清单 + `tc resend --failed`」这一半，解决"看得见失败、能单独重发"；但"失败后整批继续"始终没有定。恢复排期前需要你定语义——是"整批继续、只报失败"，还是"只给失败清单、整批仍算失败"。

### 2. 收尾把文件修改时间写回去（mtime）

**现在是什么状况**
发送端其实已经把每个文件的修改时间放进了清单，接收端收到后没有用，落盘文件的修改时间等于"收到的时间"。所以传完之后，NAS 上一整批文件的日期全是今天。

**改成什么样**
校验通过、改成正式文件名之后，把源文件的修改时间写到目标文件上；写不了就记一条日志，不影响传输。

**解决谁的什么麻烦**
用户按时间找照片、核对备份是否完整时会发现"日期全乱了"；对做增量备份的人也少了判断依据。

**能提升多少**
不是速度提升，是"传完之后文件看起来对"。额外开销是每个文件一次系统调用，预计不到总时间 1%（**未测，属推断**）。

**要付出什么代价**
小。清单字段已经现成，只改接收端收尾那一步，约几十行加测试。**不动协议，旧版本照常互通。**

**风险和副作用**
- 安卓的 SAF 落点可能不允许改时间，只能"尽力而为"，需明确降级策略。
- 某些文件系统时间精度只有 2 秒（如 exFAT），不能保证逐毫秒一致。
- 必须在"改名到最终位置之后"设置，否则同名让位改名可能把时间再改掉。

**状态**：暂停（原拟 v0.19 批内第一项，2026-11-15 排期暂停）。
**卡在哪**：需要你确认"是否在意文件日期"；如果不在意，这项可以直接不做。

### 3. 哈希缓存（接收端记住算过的指纹）

**现在是什么状况**
重复发送同一个目录时，接收端对每个"同名同大小"的已有文件都要重新读一遍、重新算指纹，才能确认"确实一样、可以跳过"。NAS 实测算指纹约 1.3 GB/s，按这个速度推算，250 GB 目录重发一次光"确认"就要约 192 秒（**推断，按实测速度线性外推**）。

**改成什么样**
接收端本地存一张小表：文件路径 + 大小 + 修改时间 → 指纹。下次三项都没变，就直接信这张表，不再读盘。

**解决谁的什么麻烦**
经常把同一个大目录往 NAS 重发的人。链路越快，"确认"占的比例越大：1 GbE 下可能只占几个百分点，10GbE 下可能占到三成以上（**推断**）。

**能提升多少**
如果命中，跳过阶段可以从"读整份数据"降到"只查文件属性"，理论上快一到两个数量级（**未测**）。但前提是真的经常重发同一目录。

**要付出什么代价**
中等：新增一个缓存模块、读写与损坏处理、开关与日志，约 200–300 行。**不动协议。**

**风险和副作用（重点）**
- 最危险的是"漏传"：如果文件内容变了、但大小和修改时间都没变（例如用 `cp -p` 覆盖、从备份还原并保留时间），缓存会误判"一样"而跳过，用户会以为传成功了。这与项目"绝不静默丢数据"的红线直接冲突。
- 缓存文件损坏、跨版本块大小变化、Windows 大小写路径，都要有降级策略。
- 就算加了"文件号"做辅助，也不能 100% 排除上述情况。

**状态**：暂停（原拟 v0.19 批内最后一项，默认关）。
**卡在哪**：恢复排期前需要你定风险等级——(A) 不做；(B) 做成默认关闭的高级开关，用户自己开；(C) 默认开启并接受极小概率漏传。我的建议是 B 或 A，不建议 C。无论选哪个，都必须带 `--verify` 强制全量开关。

### 4. Merkle 分段校验（多流之后不再整份重读）

**现在是什么状况**
现在的整文件指纹是按顺序一块一块累积算出来的。开了多流之后，块是乱序到达的，没法边收边累积，只能收完再把整份文件读一遍核对（v0.15 设计文档已写明这一点）。NAS 实测整份校验 200 MiB 约 153 ms（约 1.3 GB/s）。

**改成什么样**
把"整文件指纹"改成"由每块指纹按顺序汇总出来"的分层结构，这样乱序收完也能直接算总指纹，不必重读磁盘。

**解决谁的什么麻烦**
多流传输大文件时，收尾多出来的一遍全盘读取。NAS 上这点时间很小；手机上接收大文件时可能更明显（**未测**）。

**能提升多少**
省掉一次"读整份文件"的时间。以 NAS 实测速度算，250 GB 约 192 秒（**推断**）；但这是收尾一次性的，不是每秒都在发生。

**要付出什么代价**
中等，且**会动协议**：指纹定义一变，新旧版本算出的结果对不上，必须用能力协商隔开；已有的半成品位图也要作废重来。

**风险和副作用**
- 校验规则变复杂，出错时更难解释。
- 与"校验失败后位图不失效"的老问题叠加时，风险更高。

**状态**：待定（建议先测手机接收大文件时校验占多少，再决定）。
**卡在哪**：要你决定"是否愿意为收尾的几十秒到几分钟，承担一次协议变更与三端同版升级"。

### 5. 安卓发送端补 WifiLock

**现在是什么状况**
安卓接收时有 Wi-Fi 锁和 CPU 锁两把；发送时只有 CPU 锁，没有 Wi-Fi 锁（代码里确认）。也就是说，手机往外发文件时，Wi-Fi 网卡仍可能按省电策略打盹。

**改成什么样**
发送服务启动时也申请 Wi-Fi 锁，结束时释放；优先用系统新推荐的"低延迟"模式。

**解决谁的什么麻烦**
手机往 NAS 发大文件时，可能出现的速度抖动或中途卡住。

**能提升多少**
**未测，属推断**。之前实测手机到 NAS 的无线链路本身只有约 11 MB/s（约 88–90 Mbps），瓶颈在链路或环境，不在锁；所以这项不一定有可见提升，必须真机 A/B 才知道。

**要付出什么代价**
很小，几十行，不动协议，不影响旧版本。

**风险和副作用**
多一把锁会略微增加耗电；低延迟模式对某些机型/路由器可能无效。

**状态**：待定。
**卡在哪**：是否愿意安排一次真机 A/B（同一文件、同一位置，持锁与不持锁各三次）。如果不安排真机，这项就不该做。

### 6. 小文件不续传，直接重传

**现在是什么状况**
任何文件断了都留半成品和位图，下次按缺口续传。小文件往往只有一块，续传省下的还不如留下的半成品多。

**改成什么样**
不超过 1 个块（当前 8 MiB，跟随块大小常量走）的文件不做续传；失败后把 `.tcpart` 与 `.map` **改名隔离**到失败目录，下次整份重传。**不是删除**：项目红线禁止彻底删除任何文件，隔离出来的半成品必须能人工恢复。

**解决谁的什么麻烦**
大量小文件传输失败后，目录里残留很多 `.tcpart` 和 `.map`，看着乱、也占空间。

**能提升多少**
速度基本无感；主要是"少留垃圾"（**未测**）。

**要付出什么代价**
小：收尾时按大小判断，几十行，不动协议；隔离函数与 v0.17 的"旧半成品隔离"共用一套。

**风险和副作用**
- 阈值按"1 个块"定义，块大小变化时自动跟随，不需要另拍数字。
- 对这些文件放弃续传，重传成本最多一个块，用户基本无感。
- 被放弃的半成品只能改名隔离，严禁真删；隔离目录要有可读的说明与人工恢复办法。

**状态**：暂停（原拟 v0.19 批内第二项；恢复时须复用中断加固的隔离函数）。

### 7. 自适应块大小

**现在是什么状况**
块大小固定 8 MiB，写死在代码里，两端必须一致。

**改成什么样**
按文件大小自动选块（同类软件 Syncthing 的做法是让一个文件大约切成 1000–2000 块，块大小 128 KiB 到 16 MiB 之间）。

**解决谁的什么麻烦**
理论上是"小文件块太大浪费、大文件块太少不好并行"。

**能提升多少**
目前没有证据。实测瓶颈是链路：无线约 11 MB/s；有线 10GbE 单流约 730 MB/s 也还没到磁盘极限。现有 4 块窗口加多流已经把在途量做满。改变块大小预计收益很小（**推断**）。

**要付出什么代价**
中大：协议字段、位图兼容、三端同版，还要重做一批测试。

**风险和副作用**
块变小会增加请求次数和内存碎片；块变大则中断重传代价高。属于"越改越复杂、收益说不清"的类型。

**状态**：待定（建议维持固定 8 MiB，除非以后出现明确证据）。

### 8. 发送端预读（提前读下一块）

**现在是什么状况**
发送端收到"要第 N 块"才去读第 N 块，读和发是串行的，没有预读线程或双缓冲。历史上曾拍板"只做发送端预读"，但一直没落地；2026-11-15 已把相关文档改成实况。

**改成什么样**
发送端开一个读线程，提前把下一块读进内存，网络发完一块立刻发下一块。

**解决谁的什么麻烦**
理论上减少"读盘等待"。

**能提升多少**
**未测**。多流之后，每条流各读各的，一个流读盘时别的流在发网络，重叠已经天然存在。单流 10GbE 下可能有小幅收益，但没实测。

**要付出什么代价**
中等：多一个线程和缓冲管理，不动协议。

**风险和副作用**
内存占用上升；读线程与取消/暂停的配合要重做；出错时定位变难。

**状态**：已决定不做（2026-11-10 的决策延续，2026-11-15 文档已订正为"未落地"）。
**说明**：留档原因不是"永远不能做"，而是"目前没有证据值得做"。若以后 10GbE 单流实测证明读盘确实是瓶颈，可重新评估。

### 9. 接收端读写解耦（收包线程 + 写盘线程）

**现在是什么状况**
接收端在一条流里"等一块 → 写一块 → 再要下一块"。虽然有 4 块在途窗口，网络和写盘已经部分重叠，但同一时刻写盘会占住这条流的处理。

**改成什么样**
收包线程只管从网络收，把块丢进有界队列；单独的写盘线程按顺序落盘。

**解决谁的什么麻烦**
理论上让收包不被慢磁盘拖住。

**能提升多少**
**未测，且我判断收益很小**。NAS 实测写盘 4.3 ms/4 MiB（约 0.9 GB/s），10GbE 单流约 730 MB/s，写盘还没成为瓶颈；而 4 块在途窗口本身就在做重叠。真正瓶颈是磁盘吞吐时，多一个线程也提不高吞吐。

**要付出什么代价**
中大：核心收块循环重写，错误传播、暂停取消、校验顺序、多流都要重新对齐，约 120–200 行。

**风险和副作用**
引入队列后，"收到"和"确实写进磁盘"之间多了一个时间窗，被杀时的行为要重新验证；死锁和内存上涨的风险都集中在这类改动里。

**状态**：待定（建议先测，达不到阈值就放弃）。
**卡在哪**：需要你同意先花一次测量成本（看现有日志里"写盘"占总时间多少），再决定是否投入。若写盘占比低于约 5%，建议直接关闭这一项。

### 10. 接收端"已存在判定"并行化

**现在是什么状况**
判断"这个文件是不是已经有了"是一个文件一个文件排队算指纹。

**改成什么样**
改成多条线程同时算（和发送端扫描时的 7 线程做法一样）。

**当初为什么被看上**
重复发送大目录时，这一步可能要读完整份数据，理论上并行能省时间。

**为什么放弃**
- 用户已明确决定不做，避免为一个没有测量数据支撑的优化多开版本、多跑门禁。
- 没有打点数据证明"跳过阶段"占总时长多少；若占比很小，并行毫无意义。
- 在机械硬盘上并行读可能互相抢磁头，收益甚至为负。
- 它和"哈希缓存"解决的是同一个麻烦；缓存若不做，单独做并行也不解决漏读风险，只是快一点。

**状态**：已决定不做。
**留档目的**：以后若有人再提"并行判定"，先回看这一条，避免重复讨论。

## 三、"以后再看"之外：明确不建议再讨论的五项

| 项目 | 一句话理由 |
|---|---|
| rsync 式差分 / 滚动校验 | 通传是"一次性整份投递"，不是长期同步；差分要求接收端保留旧文件的块索引，改动巨大，只在"大文件改了几个字节"时划算，与主要场景不符。 |
| 内容寻址 / 跨文件去重 | 需要长期索引和垃圾回收，和"发完即走、不常驻"的定位冲突。 |
| FastCopy 式直接 I/O / 特权模式 | 目标文件已经预分配；直接 I/O 对大量小文件不友好，Windows 还有对齐要求，收益不确定。 |
| KDE Connect 式复用 SFTP | 等于把目录语义、同名让位、断点续传全部交给另一套协议，是重写产品而不是优化。 |
| 压缩 / QUIC / 公网中继 | 项目里已经实测或评估后否决：压缩白烧 CPU；QUIC 在干净局域网打不过 TCP；公网中继与"局域网私有传输"定位冲突。 |

## 五、附：调研中发现的一个比上述优化更该先处理的问题

不是新功能，是现有中断策略里的一个隐患，放在这里供你决定是否单独立项：

> **校验失败后，半成品位图仍然被信任。**
> 现在如果一次传输最后校验不通过，接收端不会清理也不会作废位图。下次对同一个路径重发时，它仍然认为"这些块已经收过"，不会重新请求坏块，于是校验再次失败——反复重发也救不回来，只能人工删除 `.tcpart` 和 `.map`。
> 触发场景：同名同大小但内容不同的文件、从备份还原并保留时间、断电后"位图记了但数据没真正落盘"。
> 代价估计：给位图头加一个"源文件指纹"，对不上就把旧半成品改名隔离（不删除），约几十行。
> 状态：**暂停**（原拟 v0.17，2026-11-15 全部排期暂停待重估）。原 v0.17 的四项内容即本问题的加固方案：位图 v3、身份不符隔离、校验失败作废位图、失败清单与重发。

   - **中断加固**：前提没变（位图仍 v2、无身份、无隔离），且多流让"整场失败"的爆炸半径更大，仍然必要，只是暂停。

### 6.5 现有写盘路径对机械盘是否友好

| 观察 | 结论 |
|---|---|
| 每块 8 MiB，按偏移 `seek` 后写入 | 单文件顺序传时接近顺序写，块够大，磁头寻道被摊薄 |
| 4 条流可同时写不同文件，每文件一把锁 | 机械盘上会出现多个文件区域交替写，磁头来回跳；这是当前最不友好的一点 |
| 小文件 pack 仍按各文件偏移写入 | 页缓存回写时可能变成随机写，机械盘上更明显 |
| `set_len` 预分配 | 只是把长度设大，不等于真正预留连续空间；机械盘上仍可能碎片化 |
| 没有 fsync | 断电时"位图已记、数据未落盘"的风险存在 |
| 没有任何介质判断 | 机械盘与固态盘跑同一套并发与写入策略 |

**应改的口径**：接收端在会话开始时判断落点介质；机械盘把并发流降到 1–2 条、优先"写完一个文件再下一个"、避免并行"已存在判定"；固态盘维持默认 4 条；判断不出来时取保守值并写日志。判定依据与回退见 7.0。

## 七、六项验证实验设计（只设计，不执行）

> 目的：判断"值不值得做"，不是完工验收。所有阈值是工程判断，未实测；实测数字来自仓库记录。

### 7.0 公共前提：介质判定、样本与页缓存

**介质判定（自动，不让用户选）**
- Linux：从落点路径查 `/proc/self/mountinfo` 找到挂载设备，再读 `/sys/block/<dev>/queue/rotational`；遇到 LVM/RAID/ dm 时沿 `/sys/class/block/*/slaves` 往下看，任一底层为 rotational=1 即判机械盘。
- Windows：用存储设备属性里的 seek penalty 判断；拿不到就判"未知"。
- 安卓：内置存储按闪存处理，SAF 落点按"未知"处理。
- 回退：判定失败或未知 → **保守模式**（并发 2、按文件顺序写、不开并行判定），并记录"介质未知，已降级"。
- 切换失败不得影响传输；介质判断只影响本地调度，不进协议。

**样本**
- 小文件：10,000 × 1 KiB；中文件：2,000 × 1 MiB；块边界：500 × 8 MiB；大文件：4 × 1 GiB + 1 × 10 GiB；混合：以上各一份。
- 单文件与多文件分开测；机械盘额外测"一个 10 GiB 顺序写"与"10,000 个小文件"两种极端。
- 每个样本生成后记录文件数、总字节、目录深度。

**页缓存隔离（机械盘重点）**
- 总写入量至少为接收端内存的 2 倍，保证进入磁盘受限的稳态；同时记录 `/proc/meminfo` 的 Dirty/Writeback 与 `iostat -x` 的 `await`、`aqu-sz`。
- 冷/热两轮都跑：冷轮前让设备空闲并避开刚写过的数据；热轮直接重跑。报告以冷轮为主、热轮为上限。
- 不假设可以随意用 sudo；若必须 `drop_caches`，写成"由用户在本机执行"的前置步骤，不由自动化执行。
- 不能用 O_DIRECT 改造通传本身；O_DIRECT 只可用于对照工具（如 `dd iflag=direct`）。

**重复与判读**
- 每个条件 5 次，去掉第 1 次预热，取中位数与 p10；A/B 交替执行，避免温度与缓存单向漂移。
- 统一记录：端到端 MB/s、接收端 wait/write/verify 时间、CPU、iowait、峰值内存、失败数、最终哈希是否一致。

**公共实验 P0：机械盘上的多流并发写（决定是否降并发）**
- 假设：机械盘上 4 条流写不同文件会因磁头寻道变慢；1–2 条流可能更快。
- 做法：同一批 10 GiB 数据，分别用 1 / 2 / 4 条流写 NAS 机械盘；同样条件在 NAS 固态盘重复一遍。
- 指标：端到端时间、`iostat` 的 `await`/`aqu-sz`、接收端 write 时间、CPU。
- 判读：机械盘 4 流比 2 流慢 ≥10% → 自适应规则定为"机械盘最多 2 流"；慢 5–10% → 机械盘默认 2 流；差异 <5% → 维持 4 流，不引入介质分支。
- 固态盘若 4 流明显更快，则确认"分介质"有必要；若两者都无差异，取消自适应规则，避免过度设计。
- 无效判据：任何一组数据抖动超过 20%，先排查网络与后台任务，不据此下结论。

### 7.1 Merkle 分段校验

| 项 | 内容 |
|---|---|
| 假设 | 用"块指纹按序汇总"的根，可让多流乱序收完后直接算出总指纹，省掉整份重读校验，且不降低完整性 |
| 指标 | 校验阶段耗时、端到端时间、CPU；篡改一块后是否必然失败 |
| 在哪测 | 本机回环；10GbE 电脑→NAS 机械盘与固态盘；手机接收大文件 |
| 样本 | 10 GiB 单文件（4 流）；1,000 × 8 MiB；人为改坏一块做反向测试 |
| 重复/阈值 | 5 次取中位数；校验时间下降 ≥50%（目标接近 0），端到端提升：机械盘 ≥2%、固态盘 ≥2%、手机 ≥5% 才保留 |
| 放弃 | 端到端提升 <2%，或需要改协议导致三端同版成本过高、而收益只在几秒内 |
| 环境/人手 | NAS 两种介质；手机一台；无需插线（回环与现有 10GbE 即可）；需人为制造坏块 |
| 回归证明 | 旧版本互传（能力协商）、续传位图兼容、坏块必失败、单流增量校验不变 |
| 介质影响 | 有：校验是读盘，机械盘约 150–200 MB/s、固态盘更快；两组分别给阈值 |

### 7.2 安卓发送端补 WifiLock

| 项 | 内容 |
|---|---|
| 假设 | 发送时让 Wi-Fi 不休眠，可减少速度抖动与中途停顿 |
| 指标 | 吞吐中位数与 p10、>2 秒无进展的停顿次数、10 分钟耗电与温升 |
| 在哪测 | 手机→NAS（无线）；近距离/中距离/远距离三档信号 |
| 样本 | 20 × 100 MB + 1 × 2 GB；屏幕熄灭状态下测 |
| 重复/阈值 | 每档 5 次，持锁/不持锁交替；中位数 +10% 或 p10 +20%，且停顿次数下降，才算有效 |
| 放弃 | 中位数提升 <5% 且停顿无改善；或温升/耗电明显变差 |
| 环境/人手 | 一台真机、固定路由器位置；需要人确认屏幕熄灭与电量；不需 10GbE |
| 回归证明 | 接收端行为不变、发送成功与哈希一致、无新增权限弹窗、耗电不超基线 10% |
| 介质影响 | 无（瓶颈在无线链路，与 NAS 盘无关）；但 NAS 机械盘写入是否跟得上要顺带记录 |

### 7.3 发送端预读（手机存储与 NAS 机械盘）

| 项 | 内容 |
|---|---|
| 假设 | 发送端提前读下一块，可掩盖手机闪存/机械盘的读延迟；对本来就快的 NVMe 可能无收益甚至增加内存与竞争 |
| 指标 | 发送端读等待时间、端到端 MB/s、峰值内存、CPU；接收端 `await`/`aqu-sz` |
| 在哪测 | 手机 UFS→NAS 机械盘、手机→NAS 固态盘；电脑 NVMe→NAS 机械盘、电脑→NAS 固态盘；本机回环做对照 |
| 样本 | 10 GiB 单文件；1,000 × 8 MiB；10,000 × 1 KiB；单流与 4 流各一遍 |
| 重复/阈值 | 5 次取中位数；仅当"读等待占比 ≥5%"时看收益；端到端 +5% 保留；<3% 放弃 |
| 放弃 | 手机或 NVMe 上无收益；或内存增加超过 64 MiB；或取消响应变慢 |
| 环境/人手 | 手机一台、NAS 两种介质、可插 10GbE 直连线；机械盘按 7.0 做页缓存隔离 |
| 回归证明 | 哈希一致、暂停/取消仍按块边界生效、4 流不乱序写坏、峰值内存有上限 |
| 介质影响 | 有：发送端介质（UFS/NVMe）决定读延迟；接收端机械盘要记录"突发到达"是否让 `await` 变差。若收益只出现在手机 UFS，则按发送端介质自动开启，NVMe 上关闭 |

### 7.4 接收端读写解耦（收包线程 + 写盘线程）

| 项 | 内容 |
|---|---|
| 假设 | 收包与写盘分开，能在写盘抖动时不阻塞收包；机械盘寻道尖峰时收益更明显 |
| 指标 | 收包等待时间、写队列深度、端到端时间、`iostat` 的 `await`/`aqu-sz`、内存 |
| 在哪测 | 10GbE 电脑→NAS 机械盘与固态盘；1 流与 4 流各一组；回环对照 |
| 样本 | 10 GiB 单文件；10,000 × 1 KiB；10 GiB 混合（大+小） |
| 重复/阈值 | 5 次中位数；机械盘提升 ≥10%、固态盘 ≥5% 才保留；写队列几乎不增长则视为无效 |
| 放弃 | 提升 <5%，或峰值内存增加超过 64 MiB，或中断一致性需要复杂额外机制 |
| 环境/人手 | 10GbE 直连（需插线）、NAS 两种介质、机械盘页缓存隔离（7.0） |
| 回归证明 | `kill -9` 中断后可续传、断网不产生错块、磁盘满时能报错、校验一致、暂停/取消及时 |
| 介质影响 | 有：机械盘组与固态盘组分别判定；若只有机械盘有效，则做成"机械盘启用、固态盘保持现状"的自动策略 |

### 7.5 接收端"已存在判定"并行化

| 项 | 内容 |
|---|---|
| 假设 | 多个文件同时算指纹能缩短准备阶段；但机械盘随机读可能互相抢磁头，反而更慢 |
| 指标 | 准备阶段耗时、机械盘 `await`/`aqu-sz`、CPU |
| 在哪测 | NAS 机械盘与固态盘；本机回环 |
| 样本 | 10,000 × 1 MiB；100 × 1 GiB；全部预先存在于目标目录 |
| 重复/阈值 | 5 次中位数；固态盘 ≥1.5× 才有效；机械盘要求不慢于串行（允许 ±5%） |
| 放弃 | 准备阶段占总时长 <5%，或机械盘变慢 >5%；任一出现即判定"不做" |
| 环境/人手 | NAS 两种介质；不需要插线 |
| 回归证明 | 跳过集合与串行逐文件一致；无权限/0 字节文件处理不变 |
| 介质影响 | 有：必须分机械盘/固态盘给结论；机械盘结果直接支持"不要并行判定" |
| 备注 | 该项已于 2026-11-15 决定不做；本实验只在重新开启讨论时使用 |

### 7.6 自适应块大小

| 项 | 内容 |
|---|---|
| 假设 | 大文件用更大块可减少请求开销、提高链路利用率；小文件用小块可减少浪费与重传代价 |
| 指标 | 端到端 MB/s、请求次数、峰值内存、随机中断后的重传量、机械盘顺序性 |
| 在哪测 | 本机回环；10GbE 电脑→NAS 机械盘与固态盘；手机→NAS |
| 样本 | 10 GiB 单文件；1,000 × 8 MiB；10,000 × 1 KiB；块大小 1/4/8/16/32 MiB 各构建一版 |
| 重复/阈值 | 5 次中位数；10GbE 大文件提升 ≥10% 才考虑；无线 <5% 不动；机械盘若大块明显减少 `await`，单独记录 |
| 放弃 | 真实链路上没有 ≥5% 提升，或协议/三端同版成本超过收益 |
| 环境/人手 | 需多套构建产物与三端同版；10GbE 直连；NAS 两种介质；手机一台 |
| 回归证明 | 旧版本能力协商、续传位图、小文件 pack、内存上限、校验一致 |
| 介质影响 | 有：块越大，机械盘顺序写越友好、但中断重传越贵；固态盘对块大小不敏感。结论必须分介质给出，并决定是否只在机械盘启用大块 |

## 八、结论摘要

1. **排期全部暂停**：v0.17/v0.18/v0.19 状态改为暂停，内容与顺序保留；v0.16 按已实现标注，但缺 CHANGELOG 与部署记录。
2. **现状比文档多**：0.9–0.16 的一批功能已落地，路线里的"现状盘点"明显过时；真正缺的是中断加固、介质自适应与若干"可做可不做"的优化。
3. **主链路决定优先级**：手机→NAS 机械盘时，无线链路远慢于机械盘，多流并发写的磁头问题主要出现在电脑→NAS 的 10GbE 场景；但介质自适应规则仍应做，以免换场景后踩坑。
4. **先测再改**：P0（机械盘多流并发）与 7.4、7.1 的测量成本最低、结论最直接；7.5 与 7.6 的预期收益最低，建议保持关闭。
