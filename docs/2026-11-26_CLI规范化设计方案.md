# 通传 · CLI 规范化完整设计方案（2026-11-26）

> 适用范围：`tongchuan/src/` 这个 Rust workspace。
> 输入缺口：任务描述里的「CLI 功能范围/核心用例」「技术约束（语言/框架、依赖、运行与安装方式）」两个占位符未填写，**本文一律标为「待确认」，不替用户假定**。文中凡标「现状」均为 2026-11-26 对仓库文件的实读结果；凡标「推荐」均为肥鱼基于现状的设计建议，需用户拍板。

---

## 1. 结论先行

项目**不是没有 CLI，而是已经有一套能用的 CLI**：根 crate `tongchuan` 编译出单个二进制 `tc`，`src/src/main.rs`（1218 行）里用 `env::args()` 手写参数解析，13 个命令已经覆盖了传文件、接收、发现、信任、历史、重发、离线队列、诊断、守护进程全套核心用例。

所以「做一套完整 CLI」这件事，贴合现状的做法是 **「规范化 + 补齐」而不是「重造」**：保留已经生效的命令名、参数是输出格式（这是脚本契约，见 §3），把解析层、帮助、退出码、错误分类和测试补成一套可维护的完整体系。

### 2.3 现有解析、输出、错误机制

- **解析**：`value(args,key)` / `opt(args,key)` / `values(args,key)` 三个函数线性扫 `Vec<String>`（`main.rs:35-61`）；开关靠 `args.iter().any(|a| a == "--retry")` 这种全表搜索；分发靠 `match args.first()`。
- **输出**：一行一个事件，`PREFIX k=v ...`，字段间空格分隔，值里带空格的字段放在行尾（例：`SEND ... dest=... verdict=`）。代码注释多次写明这是给脚本匹配的契约（如 `main.rs:249`「保证 verdict= 仍在行尾、脚本好匹配」）。
- **错误**：`bad()` 造 `io::ErrorKind::InvalidInput`（`main.rs:31-33`），缺参数这类错误由 `main()` 统一 `eprintln!("ERROR: {e}"); exit(1)`（`main.rs:23-29`）。panic 由 Rust 运行时以 101 退出，daemon 的 panic hook 只负责记日志（`main.rs:829`）。
- **退出码现状（2026-11-26 实测）**：`./tc version` → 0；`./tc send`（缺 `--to`）→ stderr `ERROR: missing --to`、exit 1；**裸 `tc` 与未知命令 `tc nope` → 打印 usage 到 stdout、exit 0（静默成功）**（`main.rs:1186-1201` 的 `_ => { println!("usage:"); ... Ok(()) }`）。所以严格说不是「只有 0/1」，而是「业务错误 1、用法类 0」混在一起——这是个真实隐患，见 §12。
- **帮助**：没有 `--help`/`-h`；`_ =>` 分支打印硬编码 `usage:` 十余行（`main.rs:1186-1201`）。`unwrap_or("help")` 使裸 `tc` 落到 usage，但没有 `help` 子命令分支。
- **既有 usage 笔误**：usage 行写 `tc history [--dir DIR]`（`main.rs:1192`），但代码实际读 `--history-dir`（`main.rs:301`）。照抄 usage 生成帮助会把这个错参数固化。
- **现成二进制版本漂移**：项目根的 `tc` 实测为 `1.0.0`（2026-11-26 跑 `./tc version`），源码 `Cargo.toml:7` 是 `1.3.3`。本方案测试必须以**新构建的二进制**为准，别拿根目录旧 `tc` 当基线。
- **配置优先级**：命令行 > 配置文件 > 平台默认（`trust::resolve_identity_dir`、`history_dir_of`、`diag` 解析均如此）。
- **安全**：`tc diag` 导出时脱敏（不导出管理页口令、身份私钥、明文配对码）；`TONGCHUAN-SEND` 记录只导出计数、路径替换为 `<path>`。

### 2.4 可复用模块（`crates/tc-core/src/`，CLI 应保持薄壳）

`session.rs`（会话/帧/块）、`store.rs`（落盘/断点）、`TrustStore`（`trust.rs`）、`discover.rs`、`manifest.rs`、`queue.rs`、`history.rs`、`diag.rs`、`tls.rs`（`Identity`）、`transport.rs`、`pathsafe.rs`、`retry.rs`、`hashcache.rs`、`pair.rs`、`sendjob.rs`、`daemon.rs`、`web.rs`。

**原则：CLI 层只做「解析 → 调 tc-core → 格式化输出 → 选退出码」，不重实现任何协议或业务逻辑。** 依赖方向现状已经是单向的（`tc-core` 不依赖树内任何东西），不要破坏。

## 3. 设计原则（不可让步的兼容红线）

1. **命令名、参数名、输出前缀、字段名一律不改**。现状输出被脚本、Android `TcController`（`tc_cmd send`）、Windows 壳、fpk 生命周期脚本消费；改一个字都是破坏性变更。
2. **`verdict=` 等末位字段保持在行尾**；新增字段只能插在中间或另起一行。
3. **业务全部下沉 `tc-core`**；CLI 层改动不碰协议（0.20）、不碰信任库文件格式、不碰历史 JSONL 结构。
4. **凭据零落盘**：帮助、错误、诊断输出不得出现私钥、管理口令、明文配对码、完整指纹以外的敏感值。
5. **只移不删**：替换 `main.rs` 前先备份 + 建可恢复点（见 §9）；不永久删除任何旧文件。

### 4.3 参数定义表（建议的数据结构，供帮助、校验、补全共用一份）

```rust
// src/src/cli/spec.rs（推荐新增）
pub struct ArgSpec {
    pub long: &'static str,       // "--to"
    pub short: Option<char>,      // 暂无短选项，保持 None
    pub takes_value: bool,        // --retry 为 false
    pub required: bool,
    pub default: Option<&'static str>,
    pub help: &'static str,
}
pub struct CmdSpec {
    pub name: &'static str,       // "send"
    pub group: &'static str,      // 仅用于帮助分组
    pub usage: &'static str,      // 展示用；以代码实际读的参数为准，不照抄 usage 行的笔误
    pub args: &'static [ArgSpec],
}
pub fn commands() -> &'static [CmdSpec] { /* 13 条，逐条对应 §2.2 */ }
```

这张表是**唯一事实源**：help、未知选项校验、补全脚本、测试都从它生成。**参数名以代码实际读取的为准，不照抄 usage 行**——`tc history` 的 usage 写成 `--dir`（`main.rs:1192`）而代码读 `--history-dir`（`main.rs:301`）；是否顺手修这个笔误列入 §12。它不改变 `run()` 的业务分发逻辑，只是把「参数长什么样、怎么解释」从散落的 `value()/opt()/values()` 里收拢出来。

## 5. 错误处理与退出码

### 5.1 现状（保持默认）

- `0` = 成功，**目前也用于裸 `tc` / 未知命令**（实测：打印 usage 后正常退出）；`1` = 参数缺失、连接失败、对端拒绝、配置错全部混在一起；`101` = Rust 默认 panic 退出码（hook 只记日志）。
- 错误打到 stderr 的 `ERROR: {msg}`，提示语已是「可执行的中文」（如「先跑 tc discover 查对端指纹，再加 --peer-fp 重试」）；但 usage 是打到 **stdout** 的，见 §2.3。

### 5.2 推荐细化（**默认关闭**，经 `--strict-exit` 或环境变量 `TC_STRICT_EXIT=1` 开启）

| 码 | 含义 | 触发示例 |
|---|---|---|
| 0 | 成功 | `verdict=OK` |
| 1 | 运行/业务错误（保持现状） | 传输失败、历史写入失败 |
| 2 | 用法错误 | 缺必填参数、未知选项、`--streams 99`、未知子命令（**当前裸 `tc`/未知命令是 exit 0，改它属行为变更，见 §12**） |
| 3 | 对端拒绝 | `BUSY` / `untrusted` / 版本不兼容 |
| 4 | 本地配置或权限错误 | 配置解析失败、`allow` 白名单不含落点、目录不可写 |
| 101 | panic | 保持现状（panic hook 已记录） |

**为什么默认关闭**：老脚本只判 `0/非0`，直接细化会改变行为；用开关让用户按自己节奏迁移。开关本身也要写进帮助。

### 5.3 错误对象（推荐）

把 `bad()` 升级成一个带分类的错误类型，但**对外的 stderr 文案不变**：

```rust
pub enum CliError {
    Usage(String),      // exit 2（严格模式）
    Config(String),     // exit 4
    Io(io::Error),      // exit 1；保留原 Display
    PeerRejected(String), // exit 3
}
impl From<CliError> for i32 { /* 0/1/2/3/4 */ }
```

`main()` 仍只做一件事：打印 `ERROR: <Display>`，然后按策略选退出码。

## 6. 帮助文档设计

- **总帮助** `tc --help`：简介 + 四组命令表 + 全局说明（配置优先级、退出码、诊断脱敏声明）。
- **单命令帮助** `tc send --help`：与**代码实际读取的参数**一致的 `Usage:`（不照抄 `main.rs:1192` 的 `history --dir` 笔误）+ 参数逐行说明（必填/默认/取值域）+ 1 个真实例子。
- **生成方式**：全部从 §4.3 的命令定义表生成；禁止手写第二份帮助文本。
- **文档落点**：仓库内现行文档入口只有 `docs/README.md`；新增一节「命令行 `tc`」链接到本设计文档。逐版本改动仍进 `CHANGELOG.md`（本方案若实施，按项目约定记一条）。顺带修正版本漂移：`docs/README.md:8` 与 `README.md:7` 仍写 `1.3.1`，而 `Cargo.toml:7` 已是 `1.3.3`。
- **语言**：中文为主，参数名保留英文原样。

| `tc recv --streams 0` | 用法错误（范围 1–8） |
| `tc send --to 127.0.0.1:1 --dir <tmp>` | 非 0；`SEND`/历史 `verdict=ERROR`；不产生 `.tcpart` 残留 |
| `tc discover --timeout 1` | exit 0；stdout 以 `DISCOVER count=` 开头 |
| `tc identity --dir <tmp>` | 两次调用指纹一致（同一目录） |
| 输出契约 | 按 action 分别断言末字段：`SEND` 末 `verdict=`（`main.rs:251`）、`RECV` 末 `均速=`（`:284`）、`TRUST list` 末 `platform=`（`:111`）、`PENDING` 末 `reason=`（`:127`）、`TRUST approve/revoke/rename` 末 `dir=`（`:140/:149/:155`）、`REC` 末 `reason=`（`:609`）。**不要写「trust 统一 platform=」** |
| 脱敏 | `tc diag --out <tmp>` 产物中不含私钥、`manage.pwd` 内容、明文配对码 |
| 全帮助一致性 | 遍历 spec，逐条比对 `--help` 输出与 usage 行，防漂移 |
