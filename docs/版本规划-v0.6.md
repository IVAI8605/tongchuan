## 2. 为什么是轮询而不是推送

现有代码是「同步写 + 阻塞读」的线程模型。要做服务端主动推送，必须把连接拆成读写两半（或换异步栈），
而收益只是 1 秒延迟。v0.6 只做内核，先用 `Pull{since}` 轮询（默认 700ms），把协议、去重、定序、
信任这些真正难改的部分先固化；v0.7 接安卓时再评估是否值得上推送。

## 3. 关键设计

- **id = 内容哈希前 16 位**：天然幂等，重启后靠历史预热避免把同一内容再广播一次。
- **lamport**：服务端统一改写为 `max(本地, 对端)+1`，客户端上报值只作参考，防止伪造抢「最新」。
- **origin**：以连接身份（HELLO 里的 origin）为准，消息里自报的 origin 会被覆盖。
- **敏感标记**：照存历史，但订阅端不自动写入剪贴板——避免把密码贴到别的机器。
- **超长**：>64 KiB 直接拒绝，不截断（截断等于悄悄改用户内容）。
- **未信任**：剪贴板里可能有密码，因此不提供 open 旁路；`--open` 仅用于本机自动化。

## 4. 验收

| 项 | 断言 |
|---|---|
| 去重 | 同内容推两次，历史只留一条 |
| 顺序 | 第二条事件的 lamport 大于第一条 |
| 超长 | 64 KiB+1 拒绝，错误类型 InvalidInput |
| 拒绝 | 未批准设备连接返回 PermissionDenied，原因含 untrusted |
| 暂停 | pause 15 分钟 → paused_until 有值；resume 后为 None |
| 真机 | PC 推一条 → NAS 历史出现；`tc clip status` 能看到 latest |

## 5. 风险

| 风险 | 对策 |
|---|---|
| 剪贴板内容落盘 | 默认不启动；只在已信任设备间；历史在 identity 目录，随备份走 |
| 回环（收到又推回去） | 服务端按内容哈希去重；watch 只对 `origin != 自己` 的事件写回 |
| 轮询开销 | 700ms 一条极小 JSON，单连接；事件驱动时再升级 |
| 版本门禁阻断 0.5.x | 本版三端同批升到 0.6.0，Release 说明置顶 |
