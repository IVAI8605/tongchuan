# 手机发送功能 · 版本规划

- 命名：按规范 5.2 记为 `手机发送-v0.7.md`（2026-11-13 20:18 由 `手机发送-版本规划.md` 改名，只改名不动内容）
- 制定：2026-11-12 01:30
- 优先级：**本项目最高**（用户 2026-11-12 指定：手机发送是当前最重要功能）
- 范围：Android 端「选文件 → 选目标 → 发送」全链路，含发现、信任、进度、失败处理
- 现状基线：v0.5.0；NAS 端已稳定运行（见 [服务器端-维护手册.md](./服务器端-维护手册.md)）
- 事实口径：标「实测/代码」的有据可查；标「推断」的未验证，不能当结论排期

---

## 1. 目标

让手机成为**发送端**：在同一个 Wi-Fi 下，把手机里的文件/文件夹发给 PC 或 NAS，要求：

1. 选得动：单文件、多文件、整个文件夹
2. 找得到：自动发现同网段设备，显示名称与地址
3. 发得进：沿用现有 TLS + BLAKE3 + 信任门禁，不新增协议分支
4. 看得见：进度、结果、失败原因；失败可重试
5. 不打断：切到后台仍能发完，有通知

**不做**：手机 ↔ 手机直发、外网穿透、云端中转、iOS。

## 2. 现状与约束（代码核对）

### 2.1 Android 端已有的能力

| 项 | 现状 | 依据 |
|---|---|---|
| 接收（手机当落点） | 已完成：前台服务、通知、SAF 落盘、信任 UI | `ReceiverService`、`MainActivity`、`TcNative` |
| JNI 导出 | 仅 7 个：`startReceiver` / `stopReceiver` / `statusJson` / `validateConfig` / `trustJson` / `trustApprove` / `trustRevoke` | [lib.rs](../crates/tc-jni/src/lib.rs) |
| **发送** | **完全没有**：无 JNI 方法、无 UI 入口 | 同上；MainActivity 文案为「电脑端即可向本机投递」 |
| 设备发现 | 只有「广播自己」，**没有「听别人」** | `tc-jni` 仅调用 `announce_loop`，未调用 `discover::listen` |
| 全盘文件权限 | `MANAGE_EXTERNAL_STORAGE` 已声明，且有跳转授权页的入口 | `AndroidManifest.xml` 第 23 行；`MainActivity.java` 第 119 行 |
| 版本 | 0.5.0（versionCode 500），minSdk 26 / targetSdk 35 | `adb dumpsys package` 实测 |

### 2.2 core 已有的能力（可直接复用）

| 能力 | 位置 | 说明 |
|---|---|---|
| 发送会话 | `run_sender_with(opener, paths, pair_code)` | [session.rs](../crates/tc-core/src/session.rs) 已实现，PC/CLI 在用 |
| TLS 客户端 | `TlsOpener` + `client_config_with_identity` | 手机发送时**必须带本机证书**，否则接收端按「未提供证书」拒绝 |
| 目录打包 | `build_manifest(&[PathBuf], device)` | **路径式**：`fs::read_dir` 递归 |
| 信任门禁 | 接收端 `TrustGate` | 手机会被 NAS/PC 的信任表拦；需对端批准手机指纹 |
| 断点续传 | 接收端 `.tcpart` + 位图 | 发送端无状态，重试即续传 |

### 2.3 关键约束

1. **协议同版**：0.x 阶段小版本即协议版本，手机与对端必须同为 0.5.x（发版时三端一起动）。
2. **目录打包是路径式**：若要支持 SAF `content://` 选择，需要给发送端补一层「文件来源」抽象；这是本规划最大的技术分叉（见 §4）。
3. **手机发不出文件的最短路径**：`MANAGE_EXTERNAL_STORAGE` + 路径式打包 —— 改动最小，但依赖用户手动授予「所有文件访问」。
4. **Doze/Wi-Fi**：已有实测结论（CHANGELOG 2026-11-11 05:41）——灭屏后持续有流量时 Wi-Fi 不失联；发送本身有流量，风险低于接收常驻。

## 3. 阶段划分

### M0.5 能力探针（2026-11-12 01:45 已完成，见 §9）

一次性程序验证「路径可读 + 组播可收 + 端口可达」三项。结果：三项均未阻断（组播实收 6 包、TCP 14ms 连通、路径列目录 196 项）。结论与缺口见 §9，可进入 M1。

### M1 打通发送（2026-11-12 01:50 已完成，见 §10）

**目标**：手机能把一个目录发到 PC/NAS 并落盘成功。

- JNI 新增 `send(String target, String[] paths, String pairCode)`：内部加载本机身份、构造 `TlsOpener`、调 `run_sender_with`，返回 JSON（txnId / files / bytes / verdict / reason）
- 前置：引导用户授予「所有文件访问」权限（已有入口，补校验与提示）
- 调用线程：JNI 不阻塞主线程，Java 侧用后台线程 + 回调/轮询

**验收**：手机 → PC，`verdict=OK`，PC 侧 `received/` 落盘且 BLAKE3 校验通过；对端未批准时返回明确的 `untrusted <指纹>`。

### M2 目标发现与选择（2026-11-12 02:45 已完成，见 §12）

- JNI 新增 `discoverPeers(int timeoutMs)`：内部调 `discover::listen`，返回 `addr / name / fingerprint / platform`
- UI：设备列表（名称 + 地址 + 指纹前 8 位），记住上次目标
- 首次连接要求用户确认对端指纹（防中间人；指纹来源是发现报文，需人工核对一次）

**验收**：手机上能看到「服务器」与 PC；点选后可直接发送。

### M3 发送界面（M3a 进度回调 + M3b 界面 2026-11-12 03:16 已完成，见 §13 / §14）

M3 拆成两步：先补「发送进度」这个底层观测能力并单独验证（M3a），再做界面（M3b）。
理由是界面做完才发现底层给不出进度，返工成本更高。

- 文件选择：`ACTION_OPEN_DOCUMENT`（多选）+ `ACTION_OPEN_DOCUMENT_TREE`（整目录）
- 发送队列：一次多选按批次逐个发送，失败项单独重试
- 进度：轮询发送状态（core 侧已有 `CurrentTransfer` 结构，需确认发送端是否暴露进度；**未核对**）
- 结果页：成功/失败、字节数、耗时、失败原因

**验收**：从相册选 3 张图 + 1 个文件夹，全部成功；中途断网后重试能续传。

### M4 信任与配对体验

- 手机被拒时展示：对端名称、本次指纹、下一步怎么做（去管理页批准 / 用配对码）
- 支持 `pair_code` 快速配对（core 已支持，手机侧补输入框）
- 手机侧展示「已被哪些设备信任」= 本机指纹，方便用户去对端批准

**验收**：陌生手机首次发送被拒 → NAS 管理页批准 → 手机重发成功；全过程无需看日志。

### M5 后台与稳定性

- 发送走前台服务 + 通知（复用 `ReceiverService` 的通知框架，新增发送类型）
- 大文件分块已有；补「手机锁屏后仍发完」的实测
- 失败重试策略：网络类错误自动重试 1 次，其余给按钮

**验收**：1 GB 文件锁屏发送完成；灭屏 10 分钟后仍能继续。

### M6 体验增强（可延后）

- 系统分享菜单接入（从相册/文件管理器「分享到通传」）
- 最近发送历史（手机侧 JSONL，与 PC 的 `tc history` 语义一致）
- 多目标顺序发送

## 4. 技术选型：路径模式 vs SAF 流式

| 维度 | A 路径模式 | B SAF 流式 |
|---|---|---|
| 需要权限 | 「所有文件访问」（MANAGE_EXTERNAL_STORAGE） | 无需全盘权限，按用户选择授权 |
| core 改动 | 无，直接复用 `build_manifest` | 需给发送端加「文件来源」抽象（按 fd 读 + 目录遍历） |
| 上架限制 | Google Play 需申报，可能被拒 | 无 |
| 实现成本 | 低（JNI + UI 即可） | 中高（要改 manifest 构建与读取层） |
| 覆盖范围 | 手机存储里大部分路径 | 用户能通过 SAF 选到的都行 |

**建议**：M1–M3 先用 A 打通并验证全链路（旁路安装无上架顾虑），把 B 作为 M6 后的收敛项。若将来要上架，B 是必选项。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 三端版本不一致 | 直接 `version mismatch`，功能不可用 | 发版时 PC / 手机 / NAS 同批；版本号单一来源 |
| 手机全盘权限体验 | 用户拒绝授权就用不了 | 选择器优先 SAF；路径模式作为「高级」开关 |
| Doze 中断发送 | 大文件发到一半停 | 前台服务 + WakeLock（接收端已有先例）；失败重试 |
| 手机 IP 变化 | 记住的目标失效 | 发送前用发现结果校正地址；或按指纹重连 |
| 对端信任表为空 | 首次全被拒，用户以为坏了 | M4 的错误提示必须给出可操作路径 |
| JNI 线程与内存 | 主线程阻塞、大列表 OOM | 发送在后台线程；分批传路径 |

## 9. M0.5 能力探针结果（2026-11-12 01:45 实测）

探针：一次性 Rust 程序（零依赖，静态链接后推送到 `/data/local/tmp/probe`），源码在仓库外的工作副本里（不进仓库）。设备：测试机 / Android 16 / Wi-Fi `REDACTED`。

| # | 检查 | 命令 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | 网络可达 NAS | `probe tcp <NAS内网IP>:53318` | `TCP OK in 14ms` | **PASS** 传输端口可达（只做三次握手，未涉 TLS） |
| 2 | 收发现公告 | `probe listen 13` | **收到 6 个包**，`from=<NAS内网IP>`，报文头 `{"device":{"id":"<设备ID>","name":"<NAS设备名>"...` | **PASS** 组播加入成功（`JOIN_MULTICAST ok=true`），报文是本项目的公告 |
| 3 | 路径列目录 | `probe list /storage/emulated/0` | `LIST OK count=196`，`DCIM/` 下可见 `Camera` 等子目录与文件大小 | **PASS（代理指标）** |

### 9.1 第 3 项的证据强度与缺口

- 已核实：应用 `MANAGE_EXTERNAL_STORAGE` 的 AppOps 状态为 **`Uid mode: allow`**（`adb shell appops get`），这是 Android 允许应用按路径访问共享存储的那个开关。
- **缺口已于 2026-11-12 01:48 补上**：装上新 JNI 后由应用进程执行 `listPath("/storage/emulated/0/DCIM")`，返回 `{"ok":true,"count":13,...}`，`Camera` 等子目录可见 —— **应用身份确实能按路径读共享存储**。

### 9.2 第 2 项的注意点

探针未持有 `MulticastLock`（那是应用层 API）。应用为提高收包率通常会持锁（现有 `ReceiverService` 已持 `WifiLock`，manifest 也声明了 `CHANGE_WIFI_MULTICAST_STATE`）。M2 实现时应持 `MulticastLock` 并复测一次收包率。

### 9.3 环境实测补充

- 手机 `REDACTED/24`，与 NAS、PC 同网段；无线网络 `REDACTED`，5 GHz，协商速率 2401 Mbps，信号 -59 dBm
- 手机 → NAS 延迟 ~12.5 ms；手机 → PC（`REDACTED`）延迟 ~5.4 ms（均 `ping` 实测）
- 探针二进制留在手机上 `/data/local/tmp/probe`，可重跑；未删除

### 9.4 结论

A 方案（路径模式）的三项前置**均未出现阻断**，可以进入 M1。M1 的第一个可验证目标定为：**应用侧 JNI 列目录成功**，把 §9.1 的缺口补上。→ **已于 01:50 完成，见 §10。**

## 10. M1 验收记录（2026-11-12 01:50，真机实测）

### 10.1 改动

| 位置 | 内容 |
|---|---|
| `crates/tc-jni/src/lib.rs` | 新增 `list_path()`、`send_json()` 与两个 JNI 导出 `listPath`、`sendJson`；复用 `run_sender_with` + `client_config_with_identity`，未改协议 |

### 10.2 实测结果

| 步骤 | 结果 |
|---|---|
| 应用身份列目录 | `{"ok":true,"count":13,...}`（`/storage/emulated/0/DCIM`）——§9.1 缺口闭环 |
| 首次发送（未批准） | `{"ok":false,"reason":"receiver is busy: untrusted <手机指纹>","selfFp":"<手机指纹>"}` |
| NAS 侧 pending | `PENDING fp=<手机指纹> platform=android reason=untrusted <手机指纹>` |
| 批准 | `trust approve --alias 手机`，`TRUST count=2` |
| 再次发送 | `{"ok":true,"verdict":"OK","files":1,"bytes":9,"blocks":1,"txnId":"18e70eee5495a2da-466f"}` |
| NAS 落盘 | `received/tc-m1-test/hello.txt`（9 字节，内容 `hello-m1`），日志 `verified=true interrupted=false` |
| NAS 历史 | `peer_platform=android`、`peer_addr=REDACTED:43550`、`roots=["tc-m1-test"]` |

### 10.3 过程中发现的问题

1. **`peer_name=unknown`**：Android 上 `local_device()` 读 `COMPUTERNAME`/`HOSTNAME` 环境变量，两个都不存在，所以对端看到的是 `unknown`。与 NAS 端当初 `HOSTNAME` 缺失同类。修法：M2 让宿主把设备名（`Build.MODEL`）传进来，或给 `local_device` 加 Android 分支。
2. **adb 传 JSON 数组会被 shell 吃掉引号**：因此探针入口加了「只给 `tc_path` 时自动拼 JSONArray」的分支。正式 UI 直接构造 JSON，不受影响。
3. **Activity 已在前台时 intent 只走 `onNewIntent`**：联调需先 `am force-stop` 再启动；正式实现不依赖这个入口。
4. 批准操作写入了 NAS 信任表（新增设备名条目）。这是 M1 验收必需的，可随时 `trust revoke` 撤销。

### 10.4 M1 结论

**PASS**。路径模式成立，手机 → NAS 的发送链路（TLS + 客户端证书 + 信任门禁 + BLAKE3 校验）全部走通，且**协议零改动**。下一步 M2：发现与设备选择。

### 11.2 实测结果

| 检查 | 结果 |
|---|---|
| 发现（新接口，持 MulticastLock） | `{"ok":true,"count":1,"peers":[{"addr":"<NAS内网IP>:53318","name":"<NAS设备名>","platform":"linux","fingerprint":"<NAS指纹>"}]}` |

### 11.3 判读

- 发现只返回 1 台（NAS）是**正确行为**：PC 端 `tc` 只在「接收模式」下才广播，当前 PC 没有常驻接收，所以不会被发现。

### 11.4 M2 结论

**PASS**。手机能发现同网段设备并拿到 `addr + name + fingerprint + platform` 四要素，足以支撑 M3 的设备选择界面。下一步 M3：发送界面（文件选择 + 队列 + 进度 + 结果）。

### 13.3 关键结论

- 进度口径是**已发字节 / 清单总字节**，按块触发；块大小 4 MiB，所以小文件只会有一个进度点，属正常。
- 进度**不进协议**，纯本地观测；对端与旧版本完全无感。
- 首版测试用 2 MB 数据导致只收到 1 个进度点（块是 4 MiB），已把测试数据改成「3 块 + 1 字节」——这个坑写进注释，避免以后又按「2 MB 应该有很多点」的直觉写测试。
- **文件入参会打破「根与入参一一对应」的假设**：`build_source_map` 原来用 `paths[rootIndex].join(rel)` 取源文件，文件按父目录归组后索引就错位了，实测报「系统找不到指定的路径」。已抽出 `plan_roots` 让清单构建与源路径映射共用同一份规则，并补了回归测试。
- 单文件落点语义：`dest/<父目录名>/<文件名>`。同一批里来自不同目录的文件会各自成为一个根，不会互相覆盖。
