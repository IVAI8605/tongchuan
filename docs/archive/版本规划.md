**为什么 v0.1 不上 TLS：** 加密不改变协议语义，但会引入 `rustls`/`rcgen` 等重依赖，第一版一旦卡在编译上就验不了协议。先把帧、清单、校验、续传、路径安全这五件事用最快的闭环证明正确，v0.2 换传输层时不动协议。

### 3.4 协议冻结项（v0.1 定死后不许随便改）

1. 帧头 20 字节：`magic(2) + type(1) + flags(1) + fileId(8, u64) + blockIndex(4) + length(4)`，`fileId` 是会话内序号。
2. 块大小 **4 MiB**；`length` 字段使得最后一块可以短于 4 MiB。
3. 控制通道走"长度前缀 + 一行 JSON"，数据通道走定长二进制帧。
4. manifest 字段：`txnId / device / roots[{id,name,mode,dirs[]}] / files[{id,rootId,relPath,size,mtime,mode,blake3,blockHashes[]}] / totalBytes / totalFiles`。
5. 选择性接收：`MANIFEST_ACK` 回 `acceptedRoots[] / skippedRoots[] / acceptedFileIds[]`。
6. 探活与待发队列的控制消息名（`PROBE` / `PROBE_ACK` / `RESUME`），**v0.1 只定义不实现**，避免 v0.4 改协议。
7. 默认端口 **53318**。

### 3.5 验收（离线三件套，顺序固定）

| 步骤 | 命令 | PASS 条件 |
|---|---|---|
| 1 构建 | `cargo build --workspace --release` | 退出码 0，产出 `tc.exe` |
| 2 测试 | `cargo test --workspace` | 全部用例通过，0 failed |
| 3 端到端 | `scripts\verify.ps1` | 回环传完样本后：目录树一致、空目录存在、多根目录不合并、每文件 BLAKE3 一致、中断 2 次后续传成功、路径穿越样本被拒 |
| 4 产物校验 | `tc version` | 输出 `0.1.0`，与 `Cargo.toml` 一致 |

**风险档判定：v0.1 全部 C 档。** 没有安装包、没有权限变更、没有设备协议、不碰用户数据目录（测试样本只写进 `临时\通传-验证\`），所以**不需要真机**，也不做 NAS/手机验证。

### 3.6 破坏性约束

- 测试脚本**只创建文件，不删除**：样本和接收产物保留在 `<本地验证目录>\<时间戳>\`，需要清理时另列清单问用户。
- 脚本里不得出现 `Remove-Item -Recurse -Force`、`del /f /s /q`、`rm -rf` 一类无条件删除。
- 同名策略默认"重命名"，测试里要断言**原文件没被覆盖**。

> 预读缓冲的决策（2026-11-10 用户拍板）：FASTCopy 的做法是「固定容量大缓冲 + 读写并行」，不是整文件进内存；只抄发送端预读，接收端保持逐块落盘以保住 `.tcpart.map` 语义。整文件进内存不做——10 GB 投递会 OOM，且占内存越多越容易被手机系统清掉，与「后台常驻 + 尽量省电」冲突。详见主规划决策 2 与本次评估结论。

### 11.2 Android 16 硬约束 → 落地选择

| 约束 | 选择 | 依据 |
|---|---|---|
| `dataSync` / `mediaProcessing` 前台服务 24 小时内累计最多 6 小时 | **只用 `connectedDevice`** | Android 15 起 `Service.onTimeout()` 会强制结束，做不了常驻 |
| Android 15+ 从 `BOOT_COMPLETED` 拉起 `dataSync` 类服务被禁 | `connectedDevice` + 无障碍服务托底 | 不在明令禁止之列，但仍受 OriginOS 自启动管理 |
| 后台网络服务必须有前台服务 | `FOREGROUND_SERVICE_CONNECTED_DEVICE` + `POST_NOTIFICATIONS` | 常驻通知删不掉，做成低优先级可折叠 |

### 11.5 核心架构点：SAF 落点抽象

**问题**：Android 10+ 分区存储下，用户选的目录是 `content://` URI，而 v0.1 起的 `store.rs` 用 `PathBuf` + `File` 直接写盘，在 Android 上不适用。

**方案（已按实际取舍调整）**：Rust 侧先把「落盘后端」抽成 `Store` trait（`PathStore` 保持原有「建目录 + 写 `.tcpart` + 校验 + 改名」行为，桌面与 NAS 完全不变）；`PartFile` 支持用外部已打开的句柄构造（`from_file`），校验改成复用同一句柄回读（`hash_reader`），为将来接 fd 留好口子。

v0.4 实际落地选了更省事的一条：**SAF 只用来选目录，把树 URI 还原成真实路径**（`DocumentsContract.getTreeDocumentId` → `/storage/emulated/0/...`），配合「所有文件访问」权限按真实路径写盘。理由是不用把每个文件句柄从 Java 回调进 Rust，也不用自己做目录树映射，代码量少一半，且只在真机上才能验证的环节更少。代价是非主存储位置（网盘、U 盘）不支持，选中时明确提示而不是给个写不进去的假选项。

**门禁**：接口隔离，桌面端 Path 行为必须完全不变；v0.1–v0.3 用例全绿才允许合入（已通过：tc-core 23 个单测 + tc-jni 3 个用例）。改动集中在 `store.rs` 与 `session.rs` 的落盘调用，不动帧格式与协议消息。

### 11.6 本轮已做的可离线部分

`crates/tc-jni`：把接收端内核包成**句柄式 API**（`start_receiver` / `stop_receiver` / `status_json` / `validateConfig`），JNI 只是薄包装。理由是 Android 端是长生命周期服务，不能每个会话重建；桌面端也能复用同一入口。核心逻辑用纯 Rust 写，所以不需要 JVM 就能编译和测试。新增 3 个用例，其中一个是真起 TLS 接收端、发一个文件、断言状态接口的会话数与字节数、再停止的全链路。

**顺带修掉一个从 v0.1 就存在的协议缺陷**：接收端漏读会话流程第 5 步的 `DONE` 就回 `VERIFY_OK`，控制连接残留未读数据，Windows 关闭时发 RST，发送端偶发收到 `ConnectionReset`。加了 tc-jni 后并行度变化才把它暴露出来。现在按流程图先读 DONE 再回裁决，全量测试与 6 项门禁复跑全绿。

### 11.10 送达通知静默失败：根因与修法（2026-11-10 17:07）

【实测】装上带通知回调的包后，两次投递都成功落盘，但 `arrived` 渠道始终不存在、通知列表只有常驻那条、无崩溃日志。

【根因】不是回调没写，而是**JNI 类加载器**：接收线程是 Rust 原生线程，`attach_current_thread` 之后 `FindClass` 用的是系统类加载器，按类名找不到 App 自己的 `com.tongchuan.ReceiverService`；调用抛异常后又被 `exception_clear()` 静默吞掉，所以既无通知也无日志。**这条要记住：原生线程回调 Java，必须先缓存 jclass 的 `GlobalRef`，不要按类名查。**

【修法】`Java_…_startReceiver` 在 Java 线程里 `find_class` → `new_global_ref` 缓存，回调只按签名 `(JJZZ)V` 调用；异常处理改为先 `exception_describe` 再 `clear`，同类故障以后会在 logcat 留堆栈。正常传输仍只是一次 JNI 调用，不加轮询，不破坏省电设计。

【复验要点】下次插线覆盖安装后：重启服务 → 投递一个小目录 → `dumpsys notification` 里应出现 `channel=arrived`、`id=2001+`，且锁屏状态下 `mWakefulness` 仍为 `Asleep`。
