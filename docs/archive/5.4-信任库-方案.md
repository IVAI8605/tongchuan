# 5.4 信任库方案

- 制定：2026-11-10 20:55
- 状态：P1 已完成并本地提交（1987e3d）；P2 已本地提交（7f58765）；P3 于 2026-11-11 00:46 实施（Android 侧门禁 + 信任 UI + 版本升 0.5.0），真机验证待插线
- 决策来源：用户 2026-11-10 已拍板的五条口径（见第 2 节），本文件按此展开

## 1. 要解决的问题（现状，均有代码依据）

1. 接收端 TLS 用 `with_no_client_auth()`（`crates/tc-core/src/tls.rs` 的 `server_config`），发送方不出示证书，
   接收端拿不到「发送方是谁」的密码学证据。
2. `Control::Hello` 里的 `DeviceInfo`（name/id/platform）与 `pair_code` 都是自称，可伪造；
   当前 `config.toml` 的 `pair_code = ""`，等于默认任何能连上的人都能推文件。
3. 已发现设备只存在内存 `PeerInfo` 里，重启即丢；没有别名、没有撤销，也没有「被拒绝过谁」的记录。

因此信任库不是加一张白名单那么简单，前提是让接收方能验证发送方证书指纹——即双向 TLS。

## 2. 已定口径（不再讨论）

| 编号 | 决策 |
|---|---|
| D1 | 双向 TLS 批准，但必须与 APK 同版上线；版本号与握手层都要能反映不匹配，让旧端拿到明确提示，不能只剩一句 TLS error |
| D2 | 默认 `trust_mode = "closed"`；`open` 仅作排障/老设备过渡开关，切换必须留日志 |
| D3 | `pair_code` 匹配自动入信任，**仅当 `pair_code` 非空**；空 `pair_code` 一律只能人工批准 |
| D4 | 信任存储用 JSONL 事件流，撤销是追加事件，不删行 |
| D5 | 门禁加第 8 项 TRUST，`scripts/verify.ps1` 可改 |

实施附加要求：撤销必须立刻生效（不能等下次启动才读）；管理页与 CLI 看到的状态必须一致。

## 3. 信任存储

### 3.1 位置与格式

- 文件：`<identity_dir>/trust.jsonl`（daemon 的 `identity_dir` 与 `tc recv --identity` 指向同一处）
- 一行一个事件，UTF-8，字段：

```json
{"ts":1762779600,"op":"add","fp":"<64 hex>","alias":"客厅笔记本","name":"LAPTOP-01","platform":"windows","by":"manual"}
{"ts":1762779700,"op":"rename","fp":"<64 hex>","alias":"书房台式"}
{"ts":1762779800,"op":"revoke","fp":"<64 hex>","by":"manual","note":"换设备"}
```

- `op` 只有 `add` / `rename` / `revoke`；P2 起允许 `denied`（记录被拒尝试，供「待确认」展示），不影响信任状态。
- 加载规则：按行回放，同一 `fp` 后出现的 `add` 覆盖 `revoke`（即重新批准即可恢复），`rename` 只改别名。
  无法解析的行跳过并计数，不影响其余行——旧版本或手工编辑出错不能把整张信任表读废。
- 写规则：只追加；每次追加前确保目录存在。为防半行，单次 `writeln!` 一次写入，失败只报错不改判。

### 3.2 立即生效

- `TrustStore` 记录文件 `(mtime, len)`；每次判定/查询前 stat，变了就重放。
- 因此：daemon 运行中用 `tc trust revoke` 或管理页撤销，下一场会话立刻按新状态判定，无需重启；
  CLI 与管理页读同一文件，状态天然一致。
- 成本：每场会话一次 stat，可忽略。

### 3.3 数据结构

```rust
pub struct TrustedPeer {
    pub fp: String,        // 64 hex，BLAKE3(cert DER)
    pub alias: String,     // 用户可改，展示优先用它
    pub name: String,      // 设备自称名，仅作参考
    pub platform: String,
    pub first_seen: i64,
    pub added_by: String,  // manual | pair-code | open
}
```

## 4. 会话流程（P2）

顺序固定为：TLS 握手 → 读 HELLO → 版本检查 → 信任检查 → 配对码检查 → Manifest。

1. **握手取证**：接收端 `server_config` 改为索取客户端证书，但不在握手层直接拒绝；
   自定义 `ClientCertVerifier` 全部收下，握手后取 `peer_certificates()` 算 BLAKE3 指纹。
   这样拒绝可以给出人能读懂的原因，而不是 TLS 层一句 `alert`。
2. **版本门槛**：`Control::Hello` 增加 `version`（`#[serde(default)]`，缺失即空串）。
   接收端先比对最低互通版本；不匹配回 `Busy{reason:"version ..."}`。
   同时 `HelloAck` 已经带 `version`，发送端据此提示「接收端过旧」。
   这样 PC 新 / 手机旧、PC 旧 / 手机新两种混跑都能拿到明确提示，而不是卡在握手上。
3. **信任判定**：
   - 有证书且指纹在信任表 → 放行；
   - 无证书（旧端/未带）或指纹未知：
     - `closed`：回 `Busy{reason:"untrusted <fp 前 8 位>"}`，记 `denied` 事件与日志；
     - `open`：放行，首次见到时记 `add`（`by=open`）并写日志。
4. **配对码**：`pair_code` 配置非空且与 HELLO 一致 → 自动 `add`（`by=pair-code`）后放行；
   配置为空 → 跳过这一步，未知指纹只能走人工批准。
5. **撤销**：`revoke` 事件后，下一场会话即拒；已在传输中的会话不中断（避免半截文件）。

## 5. 默认策略与日志

- `Config` 新增 `trust_mode: String`，默认 `"closed"`。
- `open` 切换必须留日志：管理页 `/api/settings` 的 POST 与配置文件加载都写一条 `warn`，
  内容含切换前后值与来源（settings / config file）。
- daemon 启动时若 `closed` 且信任表为空，写一条 `warn`，提示三种放行方式：
  `tc trust approve`、管理页批准、非空 `pair_code` 配对。

## 6. CLI

```
tc trust list   --identity DIR
tc trust pending --identity DIR          # 返回被拒记录，每指纹只留最近一次
tc trust approve <fp> [--alias NAME] --identity DIR
tc trust revoke  <fp> --identity DIR
tc trust rename  <fp> --alias NAME --identity DIR
```

- 目录解析优先级：`--identity` > `--config FILE` 的 `identity_dir` > 当前目录 `config.toml` 的 `identity_dir` > 平台默认。
  这样 CLI 默认就与 daemon 读写同一份 `trust.jsonl`；显式给了读不到的配置会直接报错，不悄悄换目录。
- 输出用固定前缀便于脚本解析：`TRUST fp=... alias=... by=... first=... last_seen=...`
- `approve` 对已信任指纹是幂等的（重复 add 事件无害）。
- 所有命令都只追加事件，不删除、不重写历史行。

## 7. 管理页与 API

- `GET /api/trust` → `{ mode, peers: [...], pending: [...] }`
- `POST /api/trust` body：`{ action: "approve"|"revoke"|"rename", fp, alias? }`
- 页面新增「信任设备」区块：别名、指纹前缀、来源（manual/pair-code/open）、首次时间、操作（改名/撤销）；
  P2 起增加「待确认」区块，显示被拒的指纹与最近尝试时间。
- 管理页与 CLI 共享同一个 `TrustStore`，不各自维护副本。

## 8. 门禁第 8 项 TRUST（P1 即加）

在 `scripts/verify.ps1` 末尾加一项，全部在临时目录内执行：

1. `tc trust approve <假指纹> --alias 门禁设备 --identity <tmp>` → 退出码 0，`list` 含别名；
2. `tc trust revoke <假指纹>` → `list` 不再列出该指纹；
3. 断言 `trust.jsonl` 仍保留 add 与 revoke 两行（撤销不删行）；
4. 管理页 `/api/trust` 返回 200 且含 `mode` 字段。

任一条失败该项 FAIL，单项失败不阻断其余项，汇总格式沿用现有 `passed/failed/skipped`。

## 10. 兼容矩阵（P2 起生效）

| 接收端 | 发送端 | 结果 |
|---|---|---|
| 新版 closed | 新版（带证书） | 按信任表放行/拒绝，拒绝原因明确 |
| 新版 closed | 旧版（无 version/证书） | `Busy{reason:"version mismatch ... 旧版（未上报版本）不兼容"}`，明确要求同版升级 |
| 新版 open | 旧版 | 版本检查先于策略，仍回版本提示；旧端须升级后才能进入 open 判定 |
| 旧版 | 新版 | 新发送端校验 `HelloAck.version` 后报「接收端过旧」，不会卡在握手 |
| 主次版本不同 | 任意 | `Busy{reason:"version mismatch ..."}`，双方都能看到需要升级 |

## 11. 风险与回滚

- 事件流只追加，误撤销可再 `approve` 恢复，不需要删文件。
- 手工编辑出错的行会被跳过并计数，不拖垮整表。
- `open` 是回滚开关：P2 出问题可临时切 `open` 放行新版设备（信任判定故障时用），但版本不兼容的旧端仍需升级；切换必须留日志、尽快切回。
- 不迁移、不删除任何既有文件；`trust.jsonl` 首次使用由 `approve` 创建。
