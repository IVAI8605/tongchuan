# 通传 v0.5.2 · 版本详细规划

- 制定：2026-11-12 10:10
- 上游：v0.5.1（2026-11-12 09:58 发版，tag `v0.5.1`）
- 定位：**0.5.x 补丁版**，只修「250 GB 量级会真出事」的两处与手机端最痛的拒绝体验；不改协议字段
- 协议口径：主次版本相同即可互通，0.5.1 ↔ 0.5.2 可互连；但 NAS 与手机建议同批更新
- 结论标注：【实测】＝本机/真机跑过；【推断】＝按机制推的，实施后必须复测确认

---

## 1. 为什么是这三件事

v0.5.1 把速度做上去了（端到端 104.6 s → 60.3 s），但按 250 GB 的设计量级重算后，剩下两个「平时看不出来、量级一上来必炸」的问题【实测数据见 `传输提速-规划.md` §13.4 / §13.5】：

| 问题 | 250 GB 时的后果 | 现有证据 |
|---|---|---|
| 位图每收一块全量重写 | 累计多写约 **12.5 GB**，另有写放大与 SSD 磨损 | 6.9 GB 用例只放大到 0.3 GB，看不出来 |
| 发送端句柄只开不关 | 5 万个 5 MB 文件 → 必然 `Too many open files`，传输中途失败 | Android 应用 FD 上限通常 1024（部分机型 4096） |

第三件是诊断缺口：接收端日志的 `等数据 + 写盘` 比手机端墙钟少 **8–14 s**【实测，§12.10】，这段时间没有归属，多半卡在 `write_frame(BLOCK_REQ)` 的阻塞上——但没数据就不能当结论。

第四件是手机发送 M4（用户已把「手机发送」定为最高优先级）：现在手机被 NAS 拒绝时只显示一段 JSON，用户不知道「被谁拒、下一步该点哪里」。这不是性能问题，是**能不能自己解决**的问题。

## 2. 任务清单

### P0-1 位图追加写（`crates/tc-core/src/store.rs`）

**现状**（`store.rs:105-139`）：`write_block` 每收一块就调 `flush_map()`，把整个 `received` 集合排序后 `fs::write` 成文本，O(块数) 写放大。

**改法**

1. `PartFile` 增加 `map_file: Option<File>`，以 `OpenOptions::new().append(true).create(true)` 打开。
2. `write_block` 改为追加一行 `idx\n`（O(1)），保留「每块落盘」语义；崩溃最多丢当前块，重传成本 4 MiB，不影响正确性。
3. **读取完全不变**：旧格式（排序后的全量块号，一行一个）与新格式（追加行）解析路径一致，`HashSet` 天然去重。这是本方案能零迁移的原因。
4. 解析失败（含 `DONE` 标记、非法行）时，除了清空 `received`，还要把位图文件截断为空，避免新块号追加在垃圾后面把下次续传搞坏。
5. `mark_done` 先释放 append 句柄再写 `DONE`——Windows 下同时持有句柄时覆盖同名文件会失败【推断，需 Windows 用例验证】。

**验收**

- 单测：① 旧格式位图（排序全量）仍能正确续传；② 写 100 块后位图行数 = 100 且与 `received` 一致；③ 重复写同一块不产生第二次请求；④ `DONE` 后按全新会话处理。
- 回环：中断续传用例（`tests/` 现有用例）全过。
- 指标：6.9 GB 用例位图写入量从约 0.3 GB 降到约 12 MB【实测对比，`fs` 计数或抓 `iostat`】。

### P0-2 发送端句柄按文件切换关闭（`crates/tc-core/src/session.rs:542-570`）

**现状**：`handles: HashMap<u64, File>` 只插不删，会话结束才释放。

**改法**：换成固定容量的 LRU（`VecDeque<u64>` + `HashMap`），容量 = 预取窗口 + 1 的余量，取 **4**。

- 命中继续复用句柄，保住「一个大文件上千块不重复 open」的收益；
- 未命中且已满时淘汰最久未用的句柄再 open；
- 正确性不依赖淘汰顺序：被淘汰的文件下次被请求时重新 open 即可。

**验收**

- 单测：构造 300 个小文件（每文件 1 块），断言发送期间同时打开的句柄数 ≤ 4（用可注入的句柄计数器统计峰值，不读平台 fd 表）。
- 真机：手机发一个 2000+ 小文件目录，`/proc/<pid>/fd` 峰值不随文件数线性上升【A 档】。

### P0-3 `req_us` 打点（`crates/tc-core/src/session.rs:1008-1045`）

在接收端两处 `write_frame(BlockReq)` 前后计时，累计 `req_us`，加入 `ReceiverReport`，会话结束日志追加 `发请求=`。

**验收**：一次 6.9 GB 传输，`等数据 + 写盘 + 发请求` 与手机端墙钟的差从 8–14 s 收敛到 1 s 内；否则说明缺口在别处，继续按数据找，不猜。

### P2 门禁与文档

- `scripts/verify.ps1` 保持 8 项全 PASS；新增的单测挂在 TEST 项内，不新开脚本。
- 更新 `传输提速-规划.md` §13.4 / §13.7 状态、`功能展望-版本路线.md` 的版本归属、`服务器端-维护手册.md` 变更时间线。

## 3. 本版明确不做

| 项 | 为什么不做 |
|---|---|
| `update_rayon`（单文件多线程哈希） | 只在「文件数 < 线程数」时才有意义；已排入 v0.6 正式排期 |
| ADPF | 收益上限约 1.8%，且只在哈希进温控的 128 s 内有效；已排入 v0.6 正式排期 |
| 多数据连接 / pack 流 | 协议级改动，且实测当前链路是硬上限，收益接近 0 |
| 剪贴板内核 | 属 v0.6，本版不碰 |
| 手机发送 M4（拒绝与配对体验） | 用户 2026-11-12 拍板移出本版，排到 v0.5.4 |
| 块大小 4 MiB → 8 MiB | 用户 2026-11-12 拍板单独一版，排到 v0.5.3（需三端同升） |

## 4. 风险与回滚

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 位图格式变更导致续传误判 | 旧 `.tcpart.map` 被新代码解析错 | 读取路径不改 + 旧格式单测；发版前用 v0.5.1 造的半成品文件做一次真实续传 |
| `mark_done` 覆盖失败（Windows 句柄占用） | 同时持有 append 句柄时 `fs::write` | 先 drop 句柄再写；Windows 用例必须覆盖 |
| LRU 淘汰引入额外 open | 请求跨文件乱序超过容量 | 容量取 4（窗口 3 之上），乱序最多跨 2 个文件；退化为性能问题而非正确性问题 |
| 手机 UI 改动带出新的崩溃路径 | 拒绝分支未覆盖 | 只改结果区文案与一个输入框，不重构界面；真机四类错误各走一次 |

回滚：三处改动互相独立，可单独 revert；NAS 侧保留 `tc.bak-*`，手机侧可重装上一版 APK。

## 6. 顺序与依赖

```
P0-3 req_us 打点（先上，给后面留数据）
 └→ P0-1 位图追加写（独立、可单测）
     └→ P0-2 句柄 LRU（独立、可单测）
         └→ 本地门禁 + NAS 部署
             └→ P1 手机 M4（真机独占时间窗）
                 └→ 真机验收 → 发版 v0.5.2
```

理由：打点最先做，后面两项改完才有基线对比；位图与句柄互不影响，可并行写、分开提交；手机 UI 放最后，避免它阻塞 core 的验证。
