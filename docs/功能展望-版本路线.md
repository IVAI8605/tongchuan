## 零、如果只做三件事

1. **多会话并发接收。** 现在 `session.rs` 是「先 accept 一条控制、再 accept 一条数据」，一次只服务一个会话。第二台设备此刻连上来，它的控制连接会被当成第一台的**数据连接**，然后因帧不匹配而整场失败。手机和电脑同时在用是常态，这不是性能问题，是能不能用的问题。
2. **发送端传输历史 + 一键重传。** 现在一次发送结束只剩一行 stdout：成功就过去了，失败原因不落盘，明天想重发必须把整条命令重新敲一遍。历史是后面「自动重试」「右键再次发送」「诊断导出」的共同地基，先有记录才谈得上补发。（本批已完成，见第五章）
3. **增量同步（只增不删）。** 同一个目录每天发一次，现在每次都要全量重扫、全量算 BLAKE3、全量重传。按 mtime + size 预筛能去掉绝大部分开销，而且天然不引入删除语义，与项目「永不彻底删除」的红线不冲突。

**剪贴板跨端同步**是用户 2026-11-10 明确指定要做的，所以它不参与「要不要做」的判断，只参与「什么时候做、做到什么程度」的判断。它的问题不在价值，在于**安卓侧的系统限制**——见第三章，其中有一条结论必须先说清：不用输入法的前提下，安卓→电脑**无法保证**做到「复制即同步」。

## 三、剪贴板跨端同步（用户指定）

### 3.1 先把口径钉死（含我的假设）

用户口径是「Windows / Android / NAS 三端自动同步」，但这句话有四种解释，我按下面这组假设设计，**任何一条不对请直接否掉**：

| 编号 | 假设 | 影响 |
|---|---|---|
| A1 | **NAS 没有剪贴板**。它是中继 + 历史仓库，只能通过 API/命令行被写入（`tc clip push`），不会自己「复制」 | 决定 NAS 侧只做服务端，不做采集端 |
| A2 | 三端共享**一条最新剪贴板流**，不是两两独立频道。任一端复制 → 其余在线端在 ≤2s 内看到 | 决定用「事件广播 + 版本比较」而不是「点对点同步」 |
| A3 | 同一时刻**默认只有一个写者**（一个人在一台设备上复制）。多端同时复制是异常路径，要定序不能合并 | 决定用 Lamport 定序，冲突时保留最新、旧的进本地历史 |
| A4 | 只同步**文本**（≤64 KiB）。图片/文件不塞进剪贴板，走现有文件通道，剪贴板里只留「文件引用 + 预览」 | 避免把 10 MB 图片塞进剪贴板导致安卓端卡死 |
| A5 | **默认关闭**，只对已信任设备生效；开启时必须显式勾选「允许同步剪贴板」 | 剪贴板里可能有密码，不能默认全开 |

若 A2 实际是「两两独立、互不打扰」，那就不需要定序，直接用点对点；若 A3 实际是「多端频繁并发写」，得加「按设备分频道 + 用户手动选择当前生效端」。这两种改法都不影响 3.4 的连接与去重设计。

### 3.2 安卓侧到底能自动到什么程度

先把平台规则和推断分开：

- **【平台规则】** Android 10（API 29）起，应用在**没有焦点、也不是默认输入法**时读剪贴板会被限制（返回空或抛异常）。这条是官方行为变更，不是某家 ROM 的土政策。
- **【平台规则】** Android 12 起，应用读剪贴板时系统会弹隐私提示；Android 13 起有剪贴板内容浮层预览，并支持 `EXTRA_IS_SENSITIVE` 标记让系统隐藏预览；Android 13 起系统还会在约 1 小时后自动清空剪贴板。
- **【推断·待实测】** 后台应用**写**剪贴板（`setPrimaryClip`）通常不被拦，但系统可能弹出「已复制」提示，且 OriginOS 可能额外管控。
- **【推断·待实测】** 无障碍服务在 AOSP 的剪贴板访问判定里走的是特殊身份，历史上不少剪贴板同步类应用靠它读后台剪贴板。但这条在不同 ROM 上表现不一致，**必须在 iQOO Z11 上实测**才能写进承诺。
- **【实测·项目文档 11.8】** 该机已开启第三方无障碍服务（李跳跳），说明 ROM 允许第三方无障碍常驻；但这只能证明「无障碍能开」，不能证明「无障碍能读剪贴板」。

据此，四条技术路线的实际体验差异：

| 路线 | 电脑→手机（写入） | 手机→电脑（读取） | 用户要做什么 | 稳定性 | 结论 |
|---|---|---|---|---|---|
| **A. 无障碍服务读取** | 不涉及 | **可能**做到复制即同步（待实测） | 首次开启无障碍；ROM 需允许自启动/后台常驻 | 中：被系统杀进程就断，需电池白名单 | 想要「复制即同步」只能赌这条，作为**可降级能力**排期 |
| **B. 前台服务 + 常驻通知** | 能（写剪贴板） | **不能**：服务在后台，仍读不到 | 无（但常驻通知栏） | 高：前台服务优先级高 | **必做**，它是连接保持与 PC→手机 的载体，不是读取方案 |
| **C. 磁贴 / 通知按钮 / 分享菜单** | 不涉及 | 用户点一下才发 | 每复制一次点一下 | 高：跟随用户动作，不依赖后台存活 | **必做兜底**，保证「做不到自动时也能用」 |
| **D. 输入法** | — | 能（IME 是默认输入法即豁免） | 换默认输入法 | 高 | **不做**：与产品定位冲突，也不该为了剪贴板逼用户换输入法 |

**直接回答「自动能自动到什么程度」：**

- **电脑 → 手机：可以自动。** 手机端由常驻前台服务接收事件并写剪贴板，用户不需要点。唯一不确定是 ROM 是否额外弹窗或拦截后台写，属待实测。
- **手机 → 电脑：不能保证自动。** 系统只对「前台应用」或「默认输入法」放行读取。不用输入法的前提下，只有无障碍服务这一条窄路，且未实测；**保底方案必须是「复制后点一下磁贴/通知」**，即一次点击。
- **微信输入法为什么更稳：** 它是默认输入法，天然拿到豁免，还能常驻输入法进程。我们不做输入法，就**无法在架构上追平**它的自动化程度。能做到的上限是「无障碍可用时接近自动，不可用时一键」。
- **NAS → 其它端：不适用自动。** NAS 端只能通过 API 写入，属于「脚本/网页里点一下推送」。

这一条是整个方案里最容易被误解的地方，建议在功能开关旁边直接写清楚，不要等用户发现「怎么还要点一下」才解释。

### 3.3 传输通道与协议

不复用现有文件会话。原因：现有会话是「单向、大批量、接收端拉块」的模型，而剪贴板是「双向、小消息、多端在线」；硬塞进去会把刚做完的会话语义再搅一遍。

- **独立端口（待定；必须避开传输 53318 与管理页 53319）**（TCP + 现有 TLS 1.3，指纹固定沿用），消息格式为 4 字节长度前缀 + JSON，单条 ≤ 128 KiB。
- 消息类型：`hello`（设备 id/名/能力位）、`clip`（事件）、`ack`、`ping/pong`、`bye`。
- 事件字段：`{id, origin, lamport, ts_ms, kind:"text", hash, size, preview, sensitive}`。正文单独一帧传，避免预览与正文重复。
- **拓扑：默认星型**，所有端连到「主设备」（优先选 NAS，其次第一台在线设备）；没有主设备时退化为全互联。星型把连接数从 N² 降到 N，也让 NAS 天然成为历史仓库。代价是多一跳延迟（局域网内可忽略）。

### 3.4 稳定性设计（这是用户的核心诉求）

| 维度 | 设计 | 参数 |
|---|---|---|
| **连接保持** | 每对设备一条长连接，`ping` 心跳 | 心跳 25s，60s 无 pong 判定断开 |
| **断线重连** | 指数退避 + 抖动，避免多端同时重连打爆主设备 | 1/2/4/8/16/30s 上限，±20% 抖动；恢复后立即补发未确认事件 |
| **发现与 IP 变化** | 复用现有 UDP 发现；连接断开后重新发现而不是死记旧 IP | — |
| **投递保证** | 每条事件带 id，接收端按 id 幂等；发送端等 `ack` 才移出待发队列 | 内存保留最近 20 条；未 ack 的重连后重发 |
| **重复内容去重** | BLAKE3(正文) 比对；与「本端上次广播/上次接收」相同则丢弃，不更新界面时间 | 保留最近 5 个哈希 |
| **回声抑制** | 事件带 `origin`，收到自己发的一律忽略；转发时保留原 origin | — |
| **顺序与冲突** | Lamport 计数 + (lamport, deviceId) 字典序决胜；只把「更新」的事件写入剪贴板，旧的只进本地历史 | 墙钟只用于展示，不参与比较 |
| **超大内容** | >64 KiB 或二进制 → 走文件通道落到 `clip/` 目录，剪贴板事件只带引用与 ≤512B 预览 | 接收端**不自动**把大对象写入剪贴板，只提示 |
| **弱网 / 断网** | 断网期间本地保留最新 20 条待发；恢复后按 lamport 顺序补发 | 不落盘（避免剪贴板内容留痕） |
| **失败可见性** | 托盘 tooltip / 安卓常驻通知显示「已连接 2/3 台，最后同步 17:42」；`tc clip status` 输出同样信息 | 状态必须是「随时可看」，不能只写日志 |
| **隐私** | 默认关闭；只对信任设备；TLS 1.3 全链路加密；日志只记长度 + hash 前 8 位，**不记正文**；安卓侧读 `EXTRA_IS_SENSITIVE` 事件直接不广播；提供「暂停同步 15 分钟」 | 历史默认不落盘；开启「剪贴板历史」才写，且写入前提示 |
| **系统自动清空** | Android 13 起系统约 1 小时清空剪贴板，不能假设「手机上还有」 | 同步完成后不再依赖对端剪贴板存活 |

### 3.5 依赖与排期

- **5.2 并发会话是实质前置**。理由不是协议冲突（剪贴板走独立端口），而是 daemon 现在是单线程串行 accept：NAS 端在传大文件时，剪贴板连接会排在后面，「传文件时剪贴板卡住」恰恰是用户抱怨的「不稳定」。桌面临时 `recv` 每会话独立进程，不受影响。
- **信任库是硬前置**。自动同步剪贴板 = 把可能含密码的文本广播出去，没有「只信任谁」就没有默认开启的资格。
- **安卓能力实测是唯一不确定项**，且必须占用真机与用户手动操作，不能和 v0.4 的安卓开发并行在同一时间窗。

### 3.6 必须真机验证的清单（安卓，A 档，需要用户在手机上点）

1. 开启通传的无障碍服务（设置 → 无障碍），观察 OriginOS 是否额外要求「自启动」「后台高耗电」白名单。
2. 后台读剪贴板：应用不在前台时读取，记录是返回空、抛异常、还是能读到。
3. 后台写剪贴板：电脑推送后检查手机剪贴板内容与系统提示样式。
4. 锁屏状态下剪贴板预览是否泄露内容（Android 13+ 浮层）。
5. 系统剪贴板 1 小时自动清空的实际表现。
6. 磁贴添加到快捷面板、通知按钮的可用性。
7. 前台服务在息屏 10 分钟后是否仍存活（这决定「电脑→手机」自动是否真可靠）。

以上第 2、3、7 条是决定「自动到什么程度」的关键，未实测前所有相关结论按【推断】对待。

### v0.12「强制重传 + 同名让位 + 收口 + 手机界面重排」（2026-11-15 定稿）

> 前置：v0.11 的「选择文件」「暂停/取消」两项真机验证由用户完成，结果在开工前提供；有问题先修再进本版。
> 2026-11-15 用户实测结论：单选视频发送正常、暂停/继续/取消正常；多选多个视频会明显卡顿，本版一并优化。
> 起因：v0.9 起接收端按「同路径 + 同内容」跳过已有文件，重复发同一目录会秒完成（实测 `块=0 增量跳过=59`），用户需要一条「确实再传一遍」的出口。

1. **强制重传开关**：发送端可勾选/传参「忽略已有文件」，关闭增量跳过，本次全部重传。范围：手机界面（发送区开关）、CLI（`tc send --force`）、管理页发送区；接收端不需要开关——跳过判断本来就只在接收端做，发送端带标记时接收端不跳过即可（协议加字段，随该版一起升）。
2. **文件名语义（用户 2026-11-14 明确）**：强制重传时，**本次到达的文件保留源文件名**；目标位置上的同名旧文件按既有规则改名让位（`xxx (1).ext`、`(2)`…，只改名不删除），而不是像现在这样让新文件变成 `xxx (1).ext`。
   - 只在「强制重传 + 目标同名已存在」时生效；普通发送维持现状（同内容跳过、不同内容另起名字），避免改变既有用户预期。
   - 改名过程必须可回滚：先确认旧文件的新名字空闲再改名，写新文件失败时旧文件保持可读。
3. **完成提示分口径**：发送完成要能看出「这次新传了几个 / 跳过几个」，并带落点文件夹（v0.11 已有 `destDirs`）。
4. **手机接收结果补齐**（2026-11-15 用户定入本版）：接收侧「最近接收」与常驻通知显示「跳过 N 个」、落点根目录、来源设备，与发送侧口径一致。内核已统计增量跳过数，缺口在 JNI 回传与界面展示。
5. **发现端口冲突根治**（2026-11-15 用户定入本版）：发现监听固定绑 `0.0.0.0:53318` 且未开端口复用，本机托盘在跑时第二个监听（`tc discover`、e2e 用例）必失败。现在 bind 前设置 `SO_REUSEADDR`（Linux/Android 再加 `SO_REUSEPORT`），失败时给可读原因，并补「两个监听可共存」用例；目标是 `verify.ps1` 不再要求先退托盘。
6. **测试素材**：NAS `received\时长少于5分钟` 下 52 GB 重复副本**保留**，作为本版强制重传的对照测试，测完由用户自己删除，程序不做清理。
7. **多选卡顿优化 + 摘要改口径**（2026-11-15 用户实测提出）：选多个视频时，URI 解析（含 fd 反查与缓存复制）从前台线程移到后台，界面先显示「正在读取已选的 N 项…」；待发送页不再逐条列文件名，只显示「已选择「X」文件夹的 Y 个文件」（多目录时「「X」等 K 个文件夹」），跳过项另行计数。
8. **设备与保活面板**（2026-11-15 用户定）：发现、授权（接收目录 / 所有文件访问）、信任列表，以及最上方的「信任策略」说明，全部收进一个展开面板；「常驻」「保活增强」合并进同一面板。入口在首页「保活优化」原来的位置。

### v0.17 中断策略加固（暂停，待按功能现状重估）

> 2026-11-15 重排：中断加固从候选池提为 **v0.17 正式内容**；手机指定接收位置保持 v0.16，二维码配对及其后各版顺延一版（二维码配对 → v0.18）。
> 2026-11-15 起：**暂停**，按功能现状重新评估后再定是否恢复；下列设计内容保留。

**为什么值得做（现状事实）**

- 续传判据目前只有三条：位图头里的块大小匹配、块号未越界、半成品文件长度等于清单里的 `size`。**没有源文件内容身份**——同名同大小、内容不同的文件，会被当成同一份半成品继续续传。
- 落盘用的是 `flush` 而不是 `fsync`：掉电或进程被杀时，可能出现「位图已记下该块、数据还没真正落盘」。
- 上面两条合起来会形成死循环：坏块被位图记为已收 → 校验失败 → 但位图仍被信任 → 每次重发都跳过同一批坏块 → 永久失败，用户只能手工删半成品。

**四项内容**

1. **位图头升级为 v3**：`#tc-map v3 <块大小> <文件大小> <源根哈希>`。读取时与本次清单的 `size` / `blake3` 比对，一致才允许续传；v2 头没有身份字段，按旧格式处理（丢弃位图、整份重传）。
2. **身份不符先隔离再重建**：该文件的 `.tcpart` 与 `.tcpart.map` **改名隔离**到旁边（例：`xxx.tcpart.stale-<时间戳>`、`xxx.tcpart.map.stale-<时间戳>`），**不删除**（遵守项目红线），随后按全新传输重建位图。
3. **校验失败作废位图**：整文件校验（块哈希/根哈希）失败时，同样把该文件的位图改名隔离，避免上面那条死循环；下次重发从零开始，而不是继续信任坏位图。
4. **失败清单与 `tc resend --failed`**：把失败文件（路径、原因、时间）写入传输历史，并新增 `tc resend --failed` 只重发这些文件。**可拆分**：第 4 项依赖历史结构与 CLI 解析，若评估后认为与 1–3 同批风险偏高，可先发 1–3，第 4 项留到下一批或单独补丁；拆分时历史里先只记录失败、不提供命令，并在实施 PLAN 里写明。

**边界与兼容**

- 只改本地半成品格式与收尾逻辑，**不进协议**，三端可不同版部署（但同版最省事）。
- 旧版读到 v3 头会按「头不匹配」丢弃位图，行为与现在遇到未知头一致，不会写坏文件。
- 与 v0.15 多流的关系：多流按文件加锁，同一文件的位图写入仍是串行；本项不改变并发形态。

**验收口径**

- 人工制造三种不匹配（块大小 / 文件大小 / 根哈希）各一次：续传被拒、旧半成品与位图被改名隔离、重新完整传输且校验通过。
- 模拟「位图有该块但数据是空洞或错内容」：校验失败后位图作废，重发不再跳过，最终成功。
- 断电场景无法在离线门禁复现：只承诺「不会再永久卡在坏位图上」，不承诺「断电一定能续传成功」。
- `tc resend --failed` 若随本版交付：构造一批成功+失败混合的记录，断言只重发失败项。

### v0.16「手机指定接收位置」（已交付，2026-11-15）

> 交付：配置 `[[destinations]]`（id/name/path，path 必须在 allow 内）、`HELLO_ACK.destinations`、`MANIFEST.destId`、`DESTS/DESTS_ACK` 查询；CLI `tc dests` 与 `--dest-id`；手机端「接收位置」一行可单选。实测电脑与手机都按指定标识落在备用收件目录，未知标识被拒并列出可用项；手机→NAS 1 GiB 两端 SHA-256 一致。CHANGELOG v0.16.0、门禁 8/8、测试 105 项。
> 限制：跨存储空间落点仍受 systemd `ReadWritePaths` 约束（需 root），本轮验证的是同一可写根下的第二个目录。

原定排在 v0.15 并发之后；其后的中断加固、二维码配对与三项合版均自 2026-11-15 起暂停，待按功能现状重估。

现状（改造前）：接收落点固定在接收端 `config.toml` 的 `destination`，发送方只能发到默认位置；想把这次的文件放进 NAS 的另一个存储空间，得先登到 NAS 改配置。

目标：手机在发送前能**查询**对端有哪些可用接收位置，并**指定**本次落点。

初步口径：

- 接收端上报「可用接收位置」列表：取 `allow` 白名单（NAS 上就是配置好的存储空间），可带一个人可读的显示名；不上报完整磁盘结构。
- 发送端清单里带「目标位置标识」，而不是任意路径字符串；接收端只在白名单内映射成真实目录，未知标识直接拒绝并给可读原因。
- 安全边界与现有写入白名单一致：位置列表来自配置，发送方不能凭空造一个目录。
- 兼容：旧端不认这个字段时退回默认落点，不能让 0.16 与 0.15 直接断连。
- 验收口径：手机选 NAS 的某个存储空间发送，文件实际落在该目录；指定不在白名单的位置被拒，提示能看懂。

### v0.18「二维码配对」（暂停，待按功能现状重估；原顺延自 v0.17）

用二维码把「地址 + 证书指纹（+ 可选配对码）」一次带到对端，省掉手输 IP 与抄 64 位指纹。

动手前先定三件事：

1. **码里放什么**：只放地址与指纹，还是连配对码一起放。带配对码等于把凭据显示在屏幕上，需要先想清楚谁能看到这块屏幕。
2. **扫码能力从哪来**：手机端解析、电脑端生成，是否需要新增依赖。项目约束是不引前端构建与额外运行时依赖，扫码库要按这条约束评估。
3. **与自动发现的关系**：扫码定位为自动发现失败时的兜底入口，不替代发现。

定位说明：二维码只在两台设备互相看不见时需要，而那种情况多半是网络隔离——所以本版解决的是「少手输」，不是「扫一下就能连通」。
