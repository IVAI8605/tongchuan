## 1. 基线（实测）

| 指标 | 数值 | 依据 |
|---|---|---|
| 文件 | 200 MiB 单文件（50 个 4 MiB 块） | 探针发送日志 |
| 传输耗时 | **20.31 s** | 首/末 `PROGRESS` 日志时间戳 |

## 2. 瓶颈分析

### 2.1 结构性问题：单连接 + 严格一问一答（实测代码）

- 数据连接只有 **1 条**（[session.rs](../crates/tc-core/src/session.rs) 的 `let mut data = opener.open()?`）
- 循环是「收一个 `BLOCK_REQ` → 发一个 4 MiB `BlockData` → 等下一个请求」，**零流水线**
- 于是每块的成本 = 往返延迟 + 接收端单块处理时间；吞吐上限 ≈ 4 MiB / 单块总耗时

### 2.2 接收端每块都有一次「整份位图重写」（实测代码）

[store.rs](../crates/tc-core/src/store.rs) 的 `write_block` 每收一块就调用 `flush_map()`：

```rust
fs::write(&self.map_path, text)   // open(O_TRUNC) + 写 + close，每 4 MiB 一次
```

- 位图内容是**全量已收块号**重新序列化，块越多文件越大
- 在 NAS 的 ext4 + `trimacl` + `prjquota` 卷上，每块都触发一次截断+写入+元数据更新
- **推断**：这是 406 ms/块 的主要来源之一；尚未做打点测量（见 P0）

### 2.3 BLAKE3 使用 `pure` 后端（实测配置）

[tc-core/Cargo.toml](../crates/tc-core/Cargo.toml)：

```toml
blake3 = { version = "1", features = ["pure"] }
```

- 当初是为了绕开「Windows 中文路径下 mingw ar 编译汇编失败」，代价是**放弃 SIMD/汇编实现**
- **推断**：`pure` 比 SIMD 慢数倍（量级 3–6×），这是扫描阶段烧 1.1 个核的直接原因
- 扫描是**单线程**逐文件串行哈希，大目录只能吃满一个核
- 扫描完成后传输阶段会**再读一遍所有文件**，等于全量数据读两次

### 2.4 尚未验证的可能因素

| 因素 | 为什么可疑 | 验证方式 |
|---|---|---|
| Wi-Fi 省电策略限制上行 | 78 Mbps 很像省电模式下的典型值；发送时没有持 `WifiLock`（只有接收服务持） | 对比持锁/不持锁、充电/电池两种状态 |
| 未设 `TCP_NODELAY` | 控制帧很小，Nagle + 延迟 ACK 可能叠加 | 抓包看每块的请求→首个数据字节间隔 |
| TLS 记录与写放大 | 4 MiB 一次 `write_frame` 被 rustls 切成 16 KiB 记录 | 抓包看 TCP 段大小与重传 |
| NAS 磁盘写性能 | 每块 4 MiB 顺序写是否真能到 100 MB/s | NAS 上 `dd` 顺写对比 + 传输时 `iostat` |
| 接收端每块哈希校验 | 若逐块算 BLAKE3，pure 后端在 x86 上也慢 | 打点或临时关闭逐块校验对比 |

## 3. 阶段与优先级

### P0 先测量，别猜（1 步，必须最先做）

在接收端给每块打点并输出到日志（仅数字，不含文件名）：

- `recv_wait`（等下一块请求的空闲时间）
- `write`（写 4 MiB 落盘）
- `flush_map`（位图重写）
- `hash`（若逐块哈希）
- 每 100 块汇总一行：`BLK avg_total=…ms write=… flush=… hash=…`

同时在 NAS 上并行记录 `iostat -x 1` 与 `mpstat -P ALL 1`。

**验收**：能说清 406 ms 里各段各占多少。没有这一步，后面的优化都是猜。

### P1 去掉每块位图重写（改动小、收益直接）

- 位图改为**追加式**：每块只 append 一行 `idx`（O(1)），不再整份重写
- 落盘频率降为「每 64 块或每 500 ms 一次」，异常退出最多丢最后一段进度
- 续传语义不变：启动时读追加日志重建已收集合，遇到 `DONE` 仍按全新会话处理

**验收**：P0 的 `flush_map` 占比降到 <5%；200 MiB 用例吞吐明显提升（目标 ≥ 2×）。

### P2 数据通道去往返（协议内改动，收益最大）

两条路线，先做 A、再做 B：

- **A. 请求窗口（不改协议字段）**：接收端一次下发多个 `BLOCK_REQ`（例如 8 个），发送端连续发块，把往返摊薄
- **B. 多数据连接**：数据连接数从 1 提到 N（2–4），各连接独立收块；`PathClaims` 已支持落点互斥，`DATA_HELLO` 已带 txnId，改动集中在 hub 与发送端的连接池

**验收**：单块耗时不再主导；200 MiB 在 Wi-Fi 下目标 ≥ 40 MB/s；有线千兆目标 ≥ 80 MB/s。

### P3 块大小自适应

- 4 MiB 固定块在低 RTT 下偏小；按 RTT/吞吐估算放大到 8–16 MiB，或对最后一块单独处理
- 注意与内存峰值、接收端缓冲区联动

**验收**：与 P2 合并测，确认大块不增加内存峰值（手机上 < 64 MiB 常驻增量）。

### P4 BLAKE3 提速（对应「开始阶段太占时间」）

按收益排序：

1. **去掉 `pure`，恢复 SIMD/汇编**：需要解决 Windows 中文路径下 `ar` 的问题（例如把 blake3 的 C 编译产物固定到 ASCII 临时目录，或仅在 Windows 目标使用 `pure`）。Android 用 NDK clang，本来就没有这个问题
2. **多文件并行哈希**：按 CPU 核数开线程（手机 8 核），大目录扫描时间近似按核数下降
3. **边读边算，不二次读盘**：把「扫描算哈希」与「发送读块」合并为一次读取（需要重构清单构建与发送的边界，先设计后动手）
4. **超大清单一律显示按文件进度**：已在 M3 修复了「无反馈」，这里进一步做按块上报

**验收**：扫描 2 GiB 目录 < 3 s（当前需实测基线）；扫描阶段 CPU 利用率接近但不超过核数上限。

### P5 传输路径细节

- `TCP_NODELAY`（控制帧小、频繁）
- socket 收发缓冲区显式设置（当前依赖系统默认）
- 发送/接收各用一个复用缓冲区，避免每块 `vec![0u8; BLOCK_SIZE]` 反复分配
- TLS 侧确认无额外小写放大

### P6 手机侧系统因素

- 发送期间持 `WifiLock`（`WIFI_MODE_FULL_HIGH_PERF`），与接收服务一致
- 检查厂商省电策略对前后台的限速；必要时走前台服务
- 与 M5「后台稳定」合并验证（锁屏发送）

## 9. 同类项目调研与方案评估（2026-11-12）

> 目的：在动手前确认「我们的慢」是否是行业里已有成熟解法。以下要点均来自各项目公开文档。
> 凡未标注来源的判断，都是我基于本项目代码的推断。

### 9.1 调研到的做法

| 项目 | 传输模型 | 与我们相关的关键点 |
|---|---|---|
| **Syncthing（BEP v1）** | 单一会话内做**块请求窗口**，不是一问一答 | ① 块大小按「文件大小 / 块数 < 2000」选，基准 128 KiB；大文件可启用更大块（最大 16 MiB）② 并发请求量用 **KiB 预算**限制（`maxConcurrentIncomingRequestKiB`，默认 256 MiB），而不是按块数限制 |
| **croc** | **多条 TCP 连接并行**传同一份数据 | 官方描述「parallel transfer over multiple TCP ports」，靠并发连接吃满带宽 |
| **LocalSend** | HTTP：发送端 `POST /api/localsend/v2/upload` **流式写整文件** | **没有逐块请求/应答**；连续性由单个流保证，接收端边收边写 |
| **rclone** | 多文件并行搬运 | `--transfers` 默认 4，即默认就并行 |
| **BLAKE3 官方/第三方实现** | SIMD + 多线程分块 | 标量路径约 0.35 GB/s；SIMD/并行实现可达 1.8–2.1 GB/s（数量级差异） |

### 9.2 逐条对照本项目

| 维度 | 本项目现状 | 同类做法 | 结论 |
|---|---|---|---|
| 块请求模式 | 严格一问一答，零流水线 | Syncthing 用 KiB 预算的请求窗口 | **直接抄窗口模型**，且用 KiB 预算而非固定块数，避免大块/小块配置不同导致内存失控 |
| 数据连接数 | 1 条 | croc 多 TCP 并行；rclone 默认 4 并行 | **值得做**，但优先级在窗口之后：窗口解决“等待”，多连接解决“单流上限” |
| 块大小 | 固定 4 MiB | Syncthing：<2000 块，基准 128 KiB，大文件可到 16 MiB | 我们的 4 MiB 偏大，**块数偏少导致窗口放大困难**；建议改为 1–4 MiB 自适应，配合窗口 |
| 校验粒度 | 整文件算 BLAKE3（扫描期）+ 传输期二次读 | LocalSend 基本不做逐块校验；Syncthing 有块哈希但按窗口流动 | 保留块哈希（断点续传与完整性都需要），但**不应在扫描期把整文件读完再传** |
| 校验实现 | `blake3` 的 `pure` 后端（无 SIMD）、单线程 | SIMD + 多线程 | **必改**：SIMD 恢复 + 并行化，数量级收益 |
| 落盘 | 每块重写整份位图 | 未见同类项目每块重写 | **必改**（P1），纯工程问题 |

### 9.3 一个结构性反思：我们为什么需要「请求驱动」

我们采用「接收端请求、发送端应答」是为了支撑：断点续传（只补缺口）、多设备并发时落点互斥、接收端限速/限内存。

但这也把吞吐压成了「每块一次往返」。同类项目里：

- **LocalSend 干脆不做请求**：一次流式上传整文件，靠 HTTP 自身背压；
- **Syncthing 保留请求但做成窗口**：一次发放多个请求，用 KiB 预算控制内存。

**结论**：不必推翻请求模型，**P2-A 的窗口化是性价比最高的折中**。若窗口化后仍不够，再评估「开始时下发一次缺口位图，之后发送端连续推」的推送模型（改动大，需三端同版）。

### 9.4 对优先级的调整建议

原顺序：P0 → P1 → P4-1 → P4-2 → P2-A → P2-B → …

调研后建议：

```
P0 打点（不变，先量化）
 └→ P1 位图追加式（不变，低风险）
     └→ P2-A 请求窗口（**提前**，参考 Syncthing 的 KiB 预算模型）
         └→ P4-1 去 pure + P4-2 并行哈希（与 P2-A 可并行推进）
             └→ P2-B 多数据连接（参考 croc，2–4 条）
                 └→ P3 块大小自适应（参考 Syncthing 的 <2000 块规则）
                     └→ P5 路径细节 → P6 系统因素
```

理由：
1. `P2-A` 直接命中「每块 406 ms 里的大部分是等待」这个已测事实，且不需要新增连接；
2. `P4` 与 `P2-A` 互不冲突：一个省等待、一个省 CPU，可以两个人/两条线并行；
3. `P2-B` 放在窗口之后：窗口已能把单流喂满时，多连接收益会变小，避免过度设计；
4. `P3` 放最后：块大小要配合窗口预算调，先有窗口再谈块大小更稳。

### 9.5 不采纳的方案（及理由）

| 方案 | 不采纳理由 |
|---|---|
| 换成 HTTP 流式上传（LocalSend 路线） | 要重做协议、断点续传与多设备落点互斥都要重写；收益与「窗口化」重叠，风险却大得多 |
| 引入完整 BEP 协议 | 依赖多、与现有 TLS/信任模型不匹配，学习成本高于收益 |
| 逐块不加校验（纯流式） | 会丢掉断点续传与完整性保证，属于用可靠性换速度，不接受 |
| 直接上 16 MiB 大块 | 手机上内存峰值与「最后一块」处理都要改；先窗口后大块 |

## 10. P0 打点（2026-11-12 04:05，已实现，待重启测量）

### 10.1 改了什么

| 位置 | 内容 |
|---|---|
| `tc-core/session.rs` | 接收端循环里分别累计 `wait_us`（等对端回块）与 `write_us`（写盘，含每块位图重写）；收完后的整文件校验单独累计 `verify_us`；三个字段加进 `ReceiverReport` |
| `src/main.rs` | 会话结束日志追加 `块=N 等数据=Xms 写盘=Yms 校验=Zms`（**只有数字，不含文件名**） |
| 测试 | `tc-core` 33 项、e2e 11 项全过 |

### 10.2 怎么用

1. NAS 上执行 `sudo systemctl restart tongchuan`（二进制已换好，`tc.bak-20261112-0403` 为回滚点）
2. 手机再发同一个 200 MiB 用例
3. 读一行日志即可判断 406 ms/块 的构成：
   - `等数据` 大 → 瓶颈在「一问一答」的往返结构（对应 P2-A 窗口）
   - `写盘` 大 → 瓶颈在每块位图重写/磁盘（对应 P1）
   - `校验` 大 → 收完后的整文件二次读盘（对应 P4-3 边读边算）

### 10.3 顺带确认的一个事实（与 P4 有关）

接收端**不在收块时逐块校验**，而是收完后整文件重算一遍 BLAKE3（`PartFile::verify` 会读全文件、比对根哈希与每个块哈希）。所以一次 200 MiB 传输的磁盘 I/O 实际是：发送端读 2 遍（扫描哈希 + 发送）、接收端写 1 遍 + 读 1 遍。这条为 P4-3「边读边算」提供了依据。

## 11. P0 测量结果与重大修正（2026-11-12 04:20）

### 11.1 打点数据（200 MiB，50 块）

```
会话 … 结束 verified=true interrupted=false 来源=<手机设备名> 落点=<dir> 块=50 等数据=18179ms 写盘=216ms 校验=153ms
```

| 阶段 | 总耗时 | 占比 | 每块 |
|---|---|---|---|
| **等数据**（发请求 → 收满 4 MiB） | **18179 ms** | **98.7%** | ≈ 364 ms |
| 写盘（含每块位图重写） | 216 ms | 1.2% | ≈ 4.3 ms |
| 整文件校验（BLAKE3 读 200 MiB） | 153 ms | 0.8% | — |

### 11.2 两个此前的假设被推翻

1. **「每块重写位图」不是瓶颈**：写盘总共 216 ms。P1 仍有价值（避免块数多时 O(n²) 放大），但**不是当前瓶颈**。
2. **「NAS 侧 BLAKE3 慢」不成立**：200 MiB 校验只用 153 ms ≈ **1.3 GB/s**（x86 上 pure 后端够快）。慢的是**手机侧扫描**（1.1 核、单线程、pure）。

### 11.3 关键对照实验：裸 TCP 测速

| 路径 | 方式 | 结果 |
|---|---|---|
| **手机 → NAS** | `dd if=/dev/zero … \| nc`（不经 TLS、不经本项目协议） | **11.1 MB/s**（200 MB / 17.97 s） |
| PC → NAS | python socket 直发 | **349 MB/s**（200 MB / 0.57 s） |
| 手机 → NAS（本项目） | 200 MiB 实测 | 9.8 MB/s |

**结论：瓶颈在「手机 → 局域网」这段无线链路上，不在本项目协议。**

- 本项目 9.8 MB/s 已达裸 TCP 上限（11.1 MB/s）的 **88%**，协议自身开销只有约 13%
- 手机侧链路协商 1152–2401 Mbps、RSSI -59、5 GHz 5320 MHz，但**实测有效吞吐只有约 88 Mbps**
- 因此 **P2 窗口化最多只能拿到约 +13%**，在无线链路上限没提高之前，做协议手术收益有限

### 11.4 优先级重排（据实测）

| 新顺序 | 内容 | 理由 |
|---|---|---|
| **1. P6-R 网络上限诊断（需用户配合）** | 换 AP/频段、确认是否为 mesh 弱回程、关闭手机省电/网络优化后再测 | 当前 88 Mbps 是硬上限；不解决它，代码优化天花板只有 11 MB/s |
| **2. P4-1 去 pure（Android/Linux 用 SIMD）** | 仅影响扫描速度，与网络上限无关，收益确定 | 手机扫描从 1.1 核烧几分钟降下来 |
| **3. P4-2 多文件并行哈希** | 同上，扫大目录快数倍 | 与 P4-1 叠加 |
| **4. P1 位图追加式** | 写盘已不是瓶颈，但块数极大时会出现 O(n²) | 低风险，顺手做 |
| **5. P2-A 请求窗口** | 在无线上限内最多 +13% | 等网络上限提升后再评估 |
| **6. P3 块大小 / P5 路径细节** | 同上 | 最后做 |

### 11.5 给用户的判读

- 如果你家路由器是 mesh（多节点），手机很可能连在**弱回程节点**上，88 Mbps 是典型表现；换到主路由附近复测即可验证。
- 若换到主路由后仍只有 ~90 Mbps，说明是 AP 侧或空口争用，属于环境问题，代码优化无法突破。
- 校验问题另算：手机端扫描慢是**确定可优化**的（P4-1/P4-2），与网络无关。

### 11.7 下一步（按重排后的顺序）

1. **P6-R（需你配合）**：把手机挪到主路由附近，或切到另一频段，重跑 `nc` 裸测；若从 11 MB/s 提到 40 MB/s 以上，再继续做 P2 窗口才有意义
2. **P4-2**：多文件并行哈希（可与 P6-R 并行推进，不依赖网络）

4. **P2-A**：等 P6-R 有结论后再决定是否投入

### 11.8 P6-R 复测结果：硬上限 ~90 Mbps，与信号无关（2026-11-12 04:40）

手机移到主路由附近后重测：

| 位置 | RSSI | 协商速率 | 单流裸 TCP |
|---|---|---|---|
| 原位 | -59 dBm | 1152–2401 Mbps | 11.1 MB/s |
| 主路由旁 | **-16 dBm** | 2402 Mbps | **11.2 MB/s** |

信号提升 43 dB，速度**一点没变**。再做 4 流并行对照：

```
4 个接收端各收 50 MB：2.8 + 2.9 + 2.8 + 2.8 MB/s
合计 200 MB / 18.22 s = 11.0 MB/s
```

**四流相加仍等于单流** → 不是 TCP 单流窗口/丢包问题，而是链路存在**硬性带宽上限**。

11 MB/s ≈ 88–90 Mbps，非常接近百兆以太网的线速上限（100BASE-TX 实际可用约 94 Mbps）。结合「NAS → PC 有线可达 349 MB/s」，最合理的解释是：

> **手机所连的 AP/路由器，其上行口是百兆（100 Mbps），或该 AP 是百兆回程的扩展器/弱电口交换机。**

### 11.9 结论对方案的影响（重要）

| 原计划 | 新结论 |
|---|---|
| P2-A 请求窗口 | **收益接近 0**：上限不在协议，四流已证明 |
| P2-B 多数据连接（croc 式） | **收益接近 0**：同上，已用四流实测证伪 |
| P3 块大小自适应 | 收益有限，优先级继续后移 |
| P4-2 并行哈希 | **仍然有效**（与网络无关，改善“开始慢”） |
| P1 位图追加 | 仍然有效（低风险，块极多时防 O(n²)） |
| **P6-R（网络侧）** | **唯一能真正突破 11 MB/s 的方向**：换千兆口 AP / 接主路由 5G / 别用百兆扩展器 |

**给用户的可执行检查**：

1. 看路由/AP 的 WAN/LAN 口指示灯：百兆口通常标 `100`，千兆标 `1000`
2. 若手机连的是 mesh 子节点或 Wi-Fi 放大器，确认它的**回程是有线千兆还是百兆/无线**
3. 临时验证：把 NAS 和手机接到同一台**千兆交换机**的 Wi-Fi（或用手机 USB 网络共享到 PC，再 PC→NAS）对照一次
4. 若确实是百兆设备，换千兆 AP 后重跑本条 `nc` 测试，届时再决定是否做 P2

### 12.3 三项改动的依据

| 改动 | 位置 | 依据 |
|---|---|---|
| 并行哈希（两遍走） | `manifest.rs` `hash_jobs` | 准备阶段占全程 20%，单线程 321 MB/s |
| 接收端预取窗口 2→4 | `session.rs` 接收循环 | RTT 实测 3.18/6.74/16.78 ms，单块 4 MiB 约 40 ms，一问一答每块白等一个往返 |
| 增量校验 | `session.rs` `IncVerify` | 全量校验要读 6.9 GB（4.85 s），可藏进等数据空档；续传时自动退回全量 |

窗口是**接收端单侧改动**，线上帧格式不变：发送端本来就是「收到 BLOCK_REQ 就回 BlockData」的循环，多一个在途请求能正常处理。

### 12.4 CPU 实测（传输期间逐秒采样）

| 端 | 阶段 | 实测 | 折算 |
|---|---|---|---|
| 手机（8 核，1×3.25G+3×2.5G+4×2.0G） | 哈希 | 6 s 内累计 19.85 s CPU（288–393%） | **3.3 核并行**，大核 3.2 GHz 满载 |
| 手机 | 传输 | 20–39% | **0.26 核**（8 核的 3%） |
| 服务器（4C/4T） | 传输 | utime 14.7 s + stime 10.0 s / 56 s | **0.44 核**（4 核的 11%） |

结论：**两端都不是 CPU 瓶颈**，继续调线程数没有意义。

### 12.5 准备阶段的真实上限：FUSE 读路径

3.3 个核跑满、频率 3.2 GHz，6.9 GB 哈希耗时 6.6 s → 合计 1.05 GB/s，折合每核仅 320 MB/s。BLAKE3 在 A725 上单核预期可达 ~1 GB/s，说明瓶颈不在算力。

推断（未直接测量，因 adb shell 读不到 /sdcard 深层目录）：`/storage/emulated` 是 FUSE 模拟存储，每次读要经过内核 FUSE → MediaProvider 转发 → 底层 /data，多出两次内存拷贝和上下文切换，把顺序读压在 1 GB/s 量级，UFS 的顺序读能力没有完全发挥。

可试的软件侧手段（预期收益 <10%，尚未做）：

- `hash_file` 目前用 `BufReader::new`（默认 8 KiB）再按 4 MiB 读，可改为 1 MiB 容量或直接读裸 `File`，省掉一层拷贝；
- 增大单次读块（与协议块大小解耦，纯 I/O 缓冲）。

不可做：绕开 FUSE 直读块设备（需 root）。

### 12.6 本轮结论与剩余空间

- 链路利用率 **92%（1320/1441 Mbps）**，已是 Wi-Fi 6 2x2 在干扰环境下的实用上限；
- 准备阶段撞 FUSE 读上限；
- 唯一还剩的代码项：块 4 MiB → 8 MiB（块数减半、位图写减半），预估端到端 2–3%，需两端同步升级。

### 12.7 对 §11.9 的修正

§11.9 判定「P2-A 请求窗口收益接近 0」，那是**百兆链路**下的结论。本轮在千兆链路实测：窗口 2 让网络段 98.2 → 124.5 MB/s（+27%），窗口 4 再到 131.8 MB/s。**该方案在链路不再是瓶颈后是有效的**，后续不再视为已否决项。

### 12.8 哈希并发调优（4 → 6 → 7 线程）

手机 CPU 三簇：1×A725 3.25G + 3×A725 + 4×A520。“线程数”上限按核数取，逐档实测：

| 哈希线程 | 准备耗时 | 哈希吞吐 | 有效核数（`top`） | 备注 |
|---|---|---|---|---|
| 4 | 6.6 s | 1.05 GB/s | 3.3 核（峰值 393%） | 基线 |
| 6 | 5.5 s | 1.25 GB/s | 4.3 核（峰值 459%） | |
| 7（页缓存热） | 3.78 s | 1.83 GB/s | 5.6 核（峰值 533%） | |
| 7（重启后冷缓存） | **4.02 s** | **1.72 GB/s** | 未采到 | 定稿值 |
| 8（页缓存热） | 3.52 s | 1.96 GB/s | 6.58 核（峰值 658%） | 缓存红利 |
| 8（重启后冷缓存） | **4.04 s** | **1.71 GB/s** | 6.2 核（单区间） | 与 7 无差别 |

结论：

- 4 → 7 线程让准备阶段 **6.6 s → 4.0 s（-39%）**，哈希吞吐 +64%；
- 冷缓存只比热缓存慢 0.24 s，说明收益来自真并发，不是页缓存；
- 默认值定为 **7**（`manifest.rs` `hash_jobs` 的 `clamp(1, 7)`），留一颗小核给系统中断、FUSE 转发与 Wi-Fi 收发；
- **不上 8 的依据（实测）**：冷缓存下 7 线程 4.02 s、8 线程 4.04 s，差 0.02 s 属噪声；8 线程峰值 6.2 核，看似更满，但准备时间没有变短——说明卡在 I/O 而不是核数。多占的那颗小核只会挤占系统与 FUSE 转发。

另外两项同批改动：`hash_file` 去掉 `BufReader`（每块本来就读 4 MiB，8 KiB 缓冲只多一次拷贝）；准备阶段从「一遍走完」改为「先枚举取元数据、再并行哈希」两遍，保证 `fileId` 顺序不变。

## 13. 按 250 GB 量级重新评估（2026-11-12 08:45）

本软件的设计目标量级是 **250 GB 以下**，据此重算并重排后续项。

### 13.1 时间构成推算（用当前实测速率）

| 阶段 | 计算 | 耗时 | 占比 |
|---|---|---|---|
| 准备（哈希） | 250 GB ÷ 1.96 GB/s | 128 s | 7% |
| 传输 | 250 GB ÷ 161 MB/s | 1,553 s（26 分钟） | 92% |
| 校验 | 增量校验，接近 0 | — | — |
| 合计 | — | 约 **28 分钟** | — |

### 13.2 update_rayon（单文件多线程哈希）：已排入 v0.6 正式排期

- 它解决「**单个文件**吃满多核」；我们现在的并行是「多个文件各占一线程」。
- 250 GB 若由几百上千个文件组成，任务数远超 8，跨文件并行已经吃满。
- 只有当「文件数 < 线程数」（例如 5 个 50 GB 大文件）时才有意义。
- 代价：引入 rayon（约 +5 个 crate）并开 blake3 的 rayon feature。

**结论：已排入 v0.6 正式排期。** 选在 v0.6 的依据：常规目录的跨文件并行早已吃满，只有「文件数 < 线程数」的超大单文件场景才轮得到它；与剪贴板内核同批改动，评估与回归一次做完。收益预期：5 个 50 GB 大文件的准备阶段能真正吃满多核。

### 13.3 ADPF（Performance Hint API）：已排入 v0.6 正式排期

- 250 GB 时哈希约 **128 秒全核满载**，确实会进入温控区间，ADPF 有真实价值；
- 但只影响这 128 秒（占 7%），后面 26 分钟传输 CPU 仅 0.3–0.4 核，ADPF 无从发力；
- 实现成本：跨 JNI 传哈希线程 TID + 会话生命周期管理，约 60–80 行。

**结论：已排入 v0.6 正式排期。** 选在 v0.6 的依据：按 250 GB 设计量级，哈希 128 s 全核满载必然进入温控区间，正是 ADPF 的适用场景；13.4/13.5 这类必修项已在 v0.5.2 提前消化。收益预期：上限约 0.5 分钟（全流程的 1.8%）。

### 13.4 位图每块全量重写 → 250 GB 下放大成 O(n²)（必修）

`store.rs` 的 `flush_map` 每收一块就把整份位图 `fs::write` 一次：

| 250 GB 推算 | 数值 |
|---|---|
| 块数 | 约 59,600 |
| 位图最终大小 | 约 417 KB |
| 累计重写量（平均 209 KB × 6 万块） | **约 12.5 GB** |
| 折算耗时 | 约 9 秒，另有大量写放大与 SSD 磨损 |

当前 6.9 GB 测试里只放大到 0.3 GB 级、看不出来；到 250 GB 就明显了。

**修法**：改成按块追加一行（或每 N 块批量刷盘），写入量从 12.5 GB 降到约 0.4 GB。即原规划里的 P1，本轮升级为必修。

### 13.5 发送端文件句柄无上限（必修）

`session.rs` 发送循环里：

```rust
if !handles.contains_key(&req.file_id) {
    handles.insert(req.file_id, File::open(abs)?);
}
```

每遇到新文件就 open 且**永不关闭**，直到会话结束。Android 应用 FD 上限通常 1024（部分机型 4096）。

- 250 GB / 250 个 1 GB 文件：没问题；
- 250 GB / 5 万个 5 MB 文件：**必然撞 `Too many open files`**，传输中途失败。

**修法**：请求按文件顺序到达，切到下一个文件时关掉上一个句柄，句柄数恒定在 1–2 个。

### 13.6 线程命名与优先级

- **命名已做**：哈希线程改为 `tc-hash-0..N`，`top -H`/perfetto 可直接识别。
- **优先级不做**：实测前台 App 线程 `PR=10 / NI=-10`（系统已提升到应用可得的最高档）；再往下需要 `CAP_SYS_NICE`，普通应用无权，`setpriority` 会返回 EPERM，写代码等于空操作。

### 13.7 后续优先级
