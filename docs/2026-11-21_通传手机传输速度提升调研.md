| 项目 | 内容 |
|---|---|
| 调研对象 | `AI/tongchuan/src`（通传 1.0.0，协议 0.20）手机 ↔ NAS 文件通道 |
| 调研日期 | 2026-11-21 |
| 调研人 | 肥鱼（常驻助手会话） |
| 存放位置 | `总理/` |
| 结论 | 手机测到的 **140MB/s 已是 WiFi 6 天花板附近**，代码层面能挤的主要是**发送端缺 WiFi 高性能锁**和**多流参数**；协议和分块机制本身已经做得不错，别动大结构。 |

> **证据分层**：「源码事实」= 本次实际读取仓库代码（带行号）；「实测」= 本次读取本机配置/日志；「推断」= 基于代码的合理判断；「未验证」= 需要实机跑大文件才能确认。

---

## 1 先说结论

1. **140MB/s 不是通传测出来的。** 手机历史记录里全是截图类小文件（最大约 1.3MB），没有大文件传输记录。所以那是 WiFi 链路本身的速率，通传协议还没碰到天花板。
2. **通传代码已经做了主要提速手段**：8MiB 分块、pack 批量请求、4 条并行数据流、预取窗口、哈希缓存。不是「裸 TCP 单线程」那种低效实现。
3. **真正值得改的只有一处明确缺陷**：`ReceiverService` 拿了 WiFi 高性能锁，`SendService` **没拿**——手机发文件时 WiFi 可能进省电，掉速/瞬断。改动小、风险低。
4. **其次是可调参数**：`streams` 现在 4、上限 8；但 **<8 块（64MiB）强制单流**，截图这类小文件吃不到多流，正常。
5. **不建议动** `BLOCK_SIZE` / 协议常量——按项目规范，协议变化要三端同步升版，代价远大于收益。

## 3 实测：本机日志能说明什么

- `AI/tongchuan/logs/history.jsonl`：手机（`V2551A` / `192.168.95.18`）的记录全是 **Screenshots 类单文件**，字节数 1.1KB～1.3MB。**没有大文件样本**，所以无法从历史算通传的真实吞吐。
- `AI/tongchuan/logs/daemon.log` 一条 PC→NAS 记录：`块=5000 等数据=340ms 写盘=194ms 校验=365ms`。**校验耗时接近等数据+写盘之和**，说明收尾校验在 CPU 上不便宜（虽然那次是小文件多块场景）。
- 日志里搜不到 `streams=` 行——需要按 [main.rs:229–264](<AI/tongchuan/src/src/main.rs#L229-L264>) 的 `SEND txn=... streams=N` / `RECV txn=... streams=N` 实际跑一次大文件才会出现。

## 4 提升点清单（按性价比排序）

### P0 · 给发送端补 WiFi 高性能锁 ★★★★★

- **问题**：[SendService.java:106–109](<AI/tongchuan/src/android/app/src/main/java/com/tongchuan/SendService.java#L106-L109>) 只拿了 CPU 部分唤醒锁；[ReceiverService.java:110–114](<AI/tongchuan/src/android/app/src/main/java/com/tongchuan/ReceiverService.java#L110-L114>) 明确写了「WifiLock 让网卡不做省电休眠」。
- **收益**：手机发大文件时避免 WiFi 省电/锁屏降速，减少代码里已经存在的「网络瞬断重试」（[SendService.java:132–137](<AI/tongchuan/src/android/app/src/main/java/com/tongchuan/SendService.java#L132-L137>)）。
- **改动**：照搬 `ReceiverService.acquireKeepAliveLocks()` 的 WifiLock 写法到 `SendService`，`finally` 里释放。局部改动，**不动协议、不用三端升版**。

### P1 · 实测 `streams` 1 / 4 / 8 ★★★★

- 配置已是 4、上限 8。用 [main.rs:701–702](<AI/tongchuan/src/src/main.rs#L701-L702>) 的 `tc recv --streams N` 做 A/B，不需要改代码。
- 注意 [session.rs:168–170](<AI/tongchuan/src/crates/tc-core/src/session.rs#L168-L170>)：**块数 <8（即 <64MiB）强制单流**，所以必须用 ≥100MiB 的大文件测才有意义；截图/小文件不用测。
- 推断：WiFi 单连接往往吃不满，4→8 可能再涨一点；但 8 条 TLS 连接也有握手和调度成本，**必须实测，别直接把配置改成 8**。

### P1 · 确认 pack 真的生效 ★★★

- 日志没 `streams=`，也没 `packs=` 记录可见。先跑一次大文件看 `SendReport.packs` / `streams`（[main.rs:229–237](<AI/tongchuan/src/src/main.rs#L229-L237>)）。
- 若 `packs=0`，说明两端能力协商没对上，优先修协商而不是调参数。

### P2 · 落盘 flush 批处理 ★★★（有风险）

- [store.rs:344](<AI/tongchuan/src/crates/tc-core/src/store.rs#L344>) 每块 flush + [359](<AI/tongchuan/src/crates/tc-core/src/store.rs#L359>) 位图每块 flush。改成每 N 块刷一次可减少 syscall。
- **代价**：崩溃时最多丢 N 块的续传粒度（现在是最坏丢 1 块）。属于可靠性换速度，**除非实测证明写盘是瓶颈，否则别动**。

### P2 · 多流下收尾全量校验 ★★

- [session.rs:2128](<AI/tongchuan/src/crates/tc-core/src/session.rs#L2128>) 多流时 `IncVerify` 关闭 → 收尾整文件重读重算 BLAKE3。日志里校验 365ms 说明它不轻。
- 理论上可以让每条流按块号排序喂给增量校验，但多流交错使根哈希累积复杂，**改动大、收益不确定**，排在后面。

### P3 · 不建议动的东西

| 项 | 为什么不动 |
|---|---|
| `BLOCK_SIZE` 8MiB → 16MiB | 编译期常量、HELLO 里校验，改了必须三端同步升版（项目 AGENTS.md 明文规定），为一点收益不值 |
| 协议版本 0.20 | 同上，且 Android 1.0.0 兼容范围会断 |
| 并发发送（sendjob.rs 一次一个任务） | 项目设计上刻意如此，进度条只跟一个任务，家庭场景够用 |
| TCP_NODELAY / socket buffer | 对 8MiB 大块吞吐影响很小，属于微优化 |

## 5 建议的验证步骤（本次未改代码、未跑传输）

1. 手机发一个 **≥200MiB** 的文件到 NAS，看终端/日志 `RECV ... streams=N`。
2. 同样文件，`tc recv --streams 1` 和默认 4（以及临时 8）各跑一次，对比耗时。
3. 若 4 与 1 差不多 → 瓶颈在 WiFi 链路或手机 CPU，改代码没用；若差异明显 → 多流有效，可以保留 4 或试 8。
4. 顺带看 `packs=` 是否为 0；是 0 就先查能力协商。
5. 改 P0（WifiLock）后，在**锁屏状态下**重跑大文件，看是否还出现瞬断重试。

## 6 总评

| 维度 | 结论 |
|---|---|
| 140MB/s 是否到顶 | WiFi 侧基本到顶；通传协议侧还没测过大文件，不能说「通传最多 140」 |
| 代码里最明确的坑 | **发送端缺 WifiLock**（P0），改动小、不碰协议 |
| 可调旋钮 | `streams` 1/4/8，但 <64MiB 强制单流，别拿截图测 |
| 不该碰的 | 分块大小 / 协议版本 / 并发发送模型 |
| 预期收益 | P0 主要是稳定性；P1 可能再挤 10–20%；其余不确定 |
| 下一步 | 先按 §5 实测拿到 `streams=` / `packs=` 数据，再决定改哪一处 |
