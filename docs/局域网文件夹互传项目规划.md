# 通传 · 项目规划

> 项目名：**通传** ｜ 代码目录：`<仓库目录>\`
> 目标：手机 ↔ NAS ↔ 电脑 三方互传**文件夹**，追求局域网内**最快、最稳**。
> 明确不做：不兼容 LocalSend 协议，不复刻它的界面；不做自动同步；不考虑应用商店上架合规（自用侧载）。
> 日期：2026-11-09

## 零、已确认的产品决策

| 项 | 决定 | 落地要点 |
|---|---|---|
| 日志保留 | **2 天** | 日志/历史按 2 天窗口过滤展示；旧文件与旧行**保留不删**（遵守不彻底删除任何文件）；NAS 端同时写 journald |
| 手机接收位置 | **用户可设置存放目录** | SAF 目录授权并持久化（`takePersistableUriPermission`）；每个根目录可单独指定落点 |
| 手机自动进相册 | **不做** | 只有用户显式点"保存到相册"时才走 MediaStore |
| NAS 管理页 | **要做** | 内嵌静态资源，含概览 / 历史（2 天）/ 设置 / 日志 |
| Windows 右键菜单 | **要做，子菜单形态** | 注册表 verb（不需要 COM 扩展），`发送到 → [设备列表]`；Win11 一级菜单后续再评估 |
| 自动同步 | **不做** | 只做"一次性传输 + 断点续传" |
| 后台常驻接收 | **要做** | Windows：托盘 + 局域网自动发现；Android：无障碍服务默认托底常开 + `connectedDevice` 前台服务（系统要求，二者并存）；详见第六章 |
| 无障碍引导 | **可跳过** | 首次启动全屏引导但可跳过；跳过则降级为纯前台服务模式，功能不变、更易被清理 |
| Windows 安装包 | **NSIS 传统安装** | 要写注册表 verb 和防火墙规则，MSIX 沙箱限制多，不选 |
| NAS 管理页口令 | **不做** | 只监听局域网地址；写操作只接受已配对设备 |
| 待发队列 | **10 分钟** | 场景是"人在电脑旁发完就看手机"，不需要长时间离线补收 |
| 投递模式 | **默认开** | 所有已配对设备免确认接收，可在设备详情单独关；文件上限 **10 GB**；收到响一下 + 通知，**不亮屏** |
| 默认端口 | **53318**（TCP + UDP） | 避开本机已装 LocalSend 的 53317；端口占用时顺延并写回配置 |

## 一、先把目标翻译成可验收的指标

"最快最稳"必须能测量，否则做出来只能靠感觉。建议把目标钉死成下面这张表，后面每个里程碑都对着它验收。

| 场景 | 指标 | 说明 |
|---|---|---|
| 千兆有线（电脑↔NAS） | ≥ 110 MB/s | 基本等于跑满网卡 |
| 2.5G 有线 | ≥ 250 MB/s | 单流容易吃不满，需要并行 |
| 万兆有线 | ≥ 800 MB/s | 需要多流 + 零拷贝 + 大块 |
| Wi-Fi 6（手机↔电脑） | ≥ 60 MB/s | 受信号影响大，看 90 分位 |
| 10 GB 单文件中断 3 次 | 续传成功且最终哈希一致 | 断点续传的硬指标 |
| 10 万个小文件目录 | 扫描+传输不卡死、单文件失败不拖垮整批 | 小文件是真正的难点 |
| 传输时 CPU | 万兆场景 ≤ 1 个核 | 判断有没有走零拷贝 |

## 二、同类优秀案例：能抄什么、不能抄什么

我查了目前主流的 7 个方案，按"对我们有没有参考价值"排序。

| 项目 | 传输方式 | 目录支持 | 速度表现 | 值得借鉴 | 不能照抄 |
|---|---|---|---|---|---|
| **Syncthing** | 自有 BEP 协议，块级并行，多设备互相取块 | **最强**：文件夹 + 相对路径 + 扫描数据库 | 局域网可跑满，但常驻后台吃内存和电 | 目录树模型、块级校验、增量扫描 | 它是"持续双向同步"，不是"一次性发送"；手机端耗电、配置复杂 |
| **iroh / sendme** | QUIC + BLAKE3 verified streaming（Bao 树） | 弱，基本按文件/目录打包 | 实测约 4 Gbps，CPU ~15%，**断线自动续传** | 块级哈希树、续传设计、内容寻址 | QUIC 在干净局域网里打不过 TCP（见下节数据）；依赖中继/打洞体系 |
| **LocalSend 1.18.2** | HTTPS REST，整文件流 | 目录靠 `fileName` 带斜杠前缀 | 中等，单会话、无续传 | 发现体验、一键发送、UI 思路 | 整文件流、单会话 409、无断点续传、目录不是一等公民（详见已有逆向报告） |
| **Warpinator** | 42000 注册发现，42001 传数据，多个文件打成 **tar 流**（可 gzip） | 靠 tar 保留结构 | 一般，单流且压缩吃 CPU | 极简实现、mDNS 发现 | tar+gzip 单流：不可并行、不能选择性接收、断了从头来；跨平台移植质量差 |
| **Taildrop**（Tailscale） | WireGuard 隧道 + peerapi HTTP | **不支持文件夹**，只能发文件 | 快（内核态 WireGuard） | 身份即网络、零配置配对 | 依赖 tailnet 账号体系；不能发目录；不适合"纯局域网、不想装 VPN" |
| **croc** | PAKE 口令 + 公网中继 | 支持目录（打包） | 受中继限制，跨网优先 | 口令配对体验好 | 走中继，局域网速度不是它的目标 |
| **rsync / rclone** | rsync 差分算法 / 多后端 | 强 | 单线程慢，靠多进程堆 | 增量与校验思路 | 命令行工具，手机端没法用；不适合交互式传输 |

### 从案例里提炼出的四条结论

1. **目录树必须自己在协议里表达。** 只有 Syncthing 真正把文件夹当对象；LocalSend 用字符串前缀糊弄，Warpinator 用 tar 打包，Taildrop 干脆不支持。我们要做的正是这一块，所以协议要自研。
2. **块级校验 + 块级续传是最值得抄的一条。** iroh 用 BLAKE3 哈希树做到"边收边校验、断哪补哪"，这是"稳"的核心。
3. **不要用压缩。** 传照片、视频、压缩包时 zstd/gzip 只会白烧 CPU 拖慢速度。默认关闭，只对文本类目录可选开。
4. **单流是速度天花板。** Warpinator 单 tar 流、LocalSend 整文件流都卡在这。要多连接并行。

## 三、关键技术决策（含理由）

### 决策 1：传输层用 TCP + TLS 1.3，不用 QUIC

这是整个项目最重要的一个选择，理由是实测数据而不是偏好：

- 苏黎世联邦理工 2024 年的 QUIC 实现基准测试显示：在无丢包、无额外延迟的理想环境（正是局域网），**传统 TCP 栈的吞吐能达到最好的 QUIC 实现的 3 倍**；QUIC 各实现之间差异极大，且普遍受单核 CPU 限制。
- QUIC 的优势（0-RTT、连接迁移、避免队头阻塞）主要在**有丢包、跨公网、移动切换**的场景兑现。局域网内丢包率极低，这些优势换不来损失的吞吐。
- TCP 在 Linux 上可以走 `sendfile`/`splice` 零拷贝，Windows 有 `TransmitFile`；TLS 1.3 的 AES-GCM 有 CPU 指令加速，甚至能下沉到内核（kTLS）。

**结论：主通道 TCP + TLS 1.3。** 如果后续实测发现手机 Wi-Fi 漫游场景确实需要连接迁移，再把 QUIC 作为可选备用通道，而不是一上来就上。

### 决策 2：多连接并行，而不是单连接硬扛

单条 TCP 在千兆能跑满，但 2.5G/10G 会同时撞上三个瓶颈：单核加密、单线程磁盘 IO、单连接窗口。做法：

- 控制通道 1 条（长连接，传指令和小元数据）。
- 数据通道 4~8 条（按实测带宽和 CPU 核数自适应，可在设置里调）。
- 每个文件切成 4 MiB 块，块可以在任意空闲数据通道上跑，天然实现"多文件并行 + 单大文件并行"。

### 决策 3：校验用 BLAKE3，不用 SHA-256

BLAKE3 支持多线程和 SIMD，吞吐通常是 SHA-256 的数倍；更重要的是它是**哈希树**结构，天然支持"验证第 N 块"和"从第 N 块续传"，正好对上我们的块模型。整文件根哈希 + 每块哈希两级校验。

### 决策 4：块大小 4 MiB，进度落盘到 sidecar

- 块太小：每块都有头部和哈希开销，小文件场景放大延迟。
- 块太大：中断重传代价高，内存压力大。
- 4 MiB 在千兆下约 40 ms 一块，兼顾两者。
- 断点续传靠 `.part`（数据）+ `.partmap`（已收块位图）两个文件，进程重启、断电都能续。

### 决策 5：默认不压缩

见上文。可选 `zstd -1` 只对用户显式标记的"文本/代码"目录生效。

### 决策 6：发现三条腿走路

部分路由器/AP 隔离会屏蔽组播，Android 需要 `MulticastLock`，NAS 上 avahi 不一定开，所以不能只押一种。

1. **自定义 UDP 组播 / 广播 / 本机回环**（`224.0.0.167:53318`）：报文带设备 ID、名称、证书指纹、传输端口、版本。**v0.2 已落地**，零额外依赖。
2. **手动兜底**：输入 IP、扫二维码、最近连接列表（v0.1 起就有）。
3. **mDNS**（`_tongchuan._tcp`）：标准、跨平台，但要占 5353 端口且需要额外依赖，从 v0.2 顺延到 **v0.3**。

### 决策 7：安全用"自签证书 + 指纹固定 + 首次配对码"

- 每台设备生成自签证书（**v0.2 实现用 ECDSA P-256**，ring 兼容性最稳），TLS 1.3；设备 ID 用 BLAKE3 派生，重启不变。ed25519 身份密钥留作后续可选项。
- 首次连接显示 6 位数字，双方确认一致后把指纹写入信任列表（防同一局域网内的中间人）。
- 之后连接直接校验证书指纹，不做 CA 链校验（自签必然过不了公共 CA），也**不做域名校验**（局域网 IP 会变）。
- 局域网内不引入账号体系，不做云端。
- **v0.2 落地情况**：`rustls` + 自定义 `ServerCertVerifier` 按证书 DER 的 BLAKE3 指纹固定，签名验证仍交给 ring；配对码在 HELLO 阶段校验；明文是显式降级模式。

### 决策 8：落盘三原则

1. 一律先写 `<name>.tcpart`，配套 `<name>.tcpart.map` 记已收块位图；全部块校验通过后才 `rename` 成正式文件——避免半成品被误当成完整文件。
2. 目标路径逐段清洗：拒绝 `..`、绝对路径、盘符、UNC、Windows 保留名，拼完再校验一次"是否仍在目标根目录内"。
3. 同名策略可选：`重命名（默认）/ 覆盖 / 跳过 / 合并`。默认永不覆盖。

### 决策 9：一套 Rust 内核，三端复用

协议、加解密、块调度、续传状态机全部写在 Rust 里，编成一个库：

- Windows：`tc daemon` 单二进制 + 系统自带 PowerShell 托盘外壳（v0.3 落地，不引入前端构建）；真机验收时再评估是否换原生托盘。
- Android：`cdylib` + JNI，Kotlin 只做 UI 和系统集成。
- NAS：同一个 Rust 库编成无头守护进程，systemd 托管。

这样协议只有一份实现，不会出现"电脑能传、手机不能传"的经典漂移问题。

## 四、协议设计草案（v1）

### 4.1 分层

```
┌──────────────────────────────────────┐
│ 应用层：文件夹清单、选择性接收、历史     │
├──────────────────────────────────────┤
│ 会话层：会话状态机、块调度、续传          │
├──────────────────────────────────────┤
│ 帧层：定长头 + 负载（控制帧/数据帧）      │
├──────────────────────────────────────┤
│ 传输层：1 控制连接 + N 数据连接（TLS 1.3）│
└──────────────────────────────────────┘
```

控制通道用"一行一条 JSON"最省事、最好调试（也方便日后写 CLI 和抓包排查）。数据通道用二进制帧，头部固定 24 字节左右，避免 JSON 解析开销。

### 4.2 清单（manifest）：目录树怎么表达

```json
{
  "txnId": "01J...",
  "device": { "id": "...", "name": "我的电脑", "platform": "windows" },
  "roots": [
    { "id": "r1", "name": "项目A", "mode": "send",
      "dirs": ["", "src", "src/ui", "docs/img"] },
    { "id": "r2", "name": "照片", "mode": "send", "dirs": [""] }
  ],
  "files": [
    { "id": "f1", "rootId": "r1", "relPath": "src/main.rs", "size": 18234,
      "mtime": 1762700000, "mode": 420, "blake3": "af13..." },
    { "id": "f2", "rootId": "r2", "relPath": "2026/a.jpg", "size": 4823110,
      "mtime": 1762650000, "mode": 420, "blake3": "9c02..." }
  ],
  "totalBytes": 4841344,
  "totalFiles": 2
}
```

`roots[].mode` 是发送端对该根目录的意图（`send`）；接收端在 `MANIFEST_ACK` 里用 `accept` / `skip` 回应，目录级选择性接收就靠这一对字段。

**和 LocalSend 的本质区别：**

| 维度 | LocalSend v2.2 | 本方案 |
|---|---|---|
| 目录表示 | `fileName` 字符串前缀 | 独立 `roots[] + dirs[] + relPath` |
| 空目录 | 丢失 | `dirs` 显式列出 |
| 多根目录 | 前缀冲突即合并 | 每个 root 有 id 和独立名字 |
| 根名 | 不可改（取 basename） | 接收端可改名/改落点 |
| 选择性接收 | 逐文件勾选 | **目录级**选择，展开后才到文件级 |
| 目录属性 | 无 | mtime / 权限位 |

### 4.3 会话流程

```
发送端                          接收端
  │  1. HELLO(设备信息)  ────────▶ │
  │  ◀────────  HELLO_ACK(能力位)  │
  │  2. MANIFEST         ────────▶ │   （可能几百 KB，小文件多时用 gzip 压清单本身）
  │  ◀────────  MANIFEST_ACK      │   （接收端回：接受哪些 root/dir/file）
  │  3. 建 N 条数据连接            │
  │  4. BLOCK_REQ / BLOCK_DATA ◀──▶│   （块调度双向：谁有空谁拉）
  │  5. DONE             ────────▶ │
  │  ◀────────  VERIFY_OK / FAIL   │
```

关键设计：

- **块拉取而非推送**：由接收端按自己磁盘写入速度决定拉哪个块，天然形成背压，不会因为发送端猛推导致内存爆掉。
- **断线重连**：重连后只交换 `txnId` 和对端已完成的块位图，从缺口继续，不需要重新传 manifest。
- **单会话可并发多目标**：`txnId` 是每对设备一个，和 LocalSend 的"全局单会话 409"不同。
- **默认端口 53318**（TCP + UDP）：避开本机已装 LocalSend 的 53317；占用时顺延并写回配置。v0.1 不做自动发现，靠手动指定 `IP:端口`。

### 4.4 帧格式（数据通道）

| 字段 | 长度 | 说明 |
|---|---|---|
| magic | 2 B | 固定值，防止串流误判 |
| type | 1 B | BLOCK_REQ / BLOCK_DATA / CANCEL / PING |
| flags | 1 B | 是否压缩、是否最后一块 |
| fileId | 8 B | 文件在会话内的序号 |
| blockIndex | 4 B | 块号 |
| length | 4 B | 负载长度 |
| payload | N B | 块数据 |

固定头 20 字节，4 MiB 块下头部开销可忽略。

`fileId` 是**会话内文件序号**（u64，按 manifest 的 `files[]` 顺序从 0 编号），不是 manifest 里的字符串 `id`；字符串 id 只用于 `MANIFEST_ACK` 的选择性接收。这样数据帧不用带长字符串，头部才能固定 20 字节。

## 五、三端落地方案

### 5.1 NAS（Debian 12，无 GUI）

- **形态**：单个静态链接的 Rust 二进制 + systemd unit，普通用户运行，不碰 root。
- **配置**：TOML，包含别名、端口、监听地址、**允许写入的根目录白名单**、默认落点、自动接收开关。
- **目录策略**：只允许写入白名单内的路径；每个传入的 root 名都要映射到白名单下的子目录，映射不上就拒绝——NAS 最怕变成"任意写盘入口"。
- **网络**：组播需要交换机 IGMP 放行；如果是 Docker 部署必须用 host 网络，否则发现和端口映射都会坏。
- **管理页**：内置 HTTP 服务，静态资源直接编译进二进制（不依赖外部文件）。**v0.3 落地**四块：概览（设备名/监听地址/运行时长/证书指纹/已发现设备）、历史（2 天）、设置（别名/自动接收，配对码永不返回）、日志（2 天）。不做账号体系；写设置限流 10 次每分钟。
- **可观测**：日志写本地文件，按 2 天窗口过滤展示，**旧文件与旧行保留不删**；systemd 环境下同时进 journald。
- **性能**：Linux 上走 `sendfile`，写入用 `io_uring`（v0.6 万兆调优再做，先普通文件写入）。

### 5.2 Windows

- **形态**：`tc daemon` 是核心（管理页 + TLS 常驻接收 + 发现）；Windows 侧用系统自带的 PowerShell + .NET `NotifyIcon` 做托盘常驻（v0.3 实现），零前端构建、零新增运行时依赖。
- **常驻方式**：**v0.3 落地**为 HKCU `Run` 项隐藏启动 `tray.ps1`，托盘再拉起 `tc daemon`（只写 HKCU，不需要管理员）。任务计划程序 / Windows 服务模式留作后续可选；卸载脚本默认只列清单，需 `-Confirm` 才清理。
- **右键菜单**：写注册表 verb 即可（`HKCU\Software\Classes\Directory\shell`、`*\shell`），**不需要写 COM Shell Extension**。形态用**子菜单**：`发送到 → [设备列表]`，设备多了不会把一级菜单撑爆。**v0.3 落地**：固定 5 个槽位，由 `tray.ps1` 每 30 秒从管理页读真实设备后覆写（只写不删）。注意 Windows 11 会把传统 verb 收进"显示更多选项"，若一定要出现在一级菜单，才需要 `IExplorerCommand`，那是后话。
- **防火墙**：安装时（提权）直接加两条入站规则（TCP + UDP 端口），避免首次运行弹窗——这类弹窗用户经常点"取消"，之后就成了"看不见设备"的玄学问题。
- **性能**：`TransmitFile` 零拷贝；文件打开带 `FILE_FLAG_SEQUENTIAL_SCAN`；路径统一加 `\\?\` 前缀以支持超长路径。
- **体验**：剪贴板图片直接发、传输完成气泡、拖到托盘图标即发送。

### 5.3 Android

- **形态**：Kotlin UI + JNI 调 Rust 内核。
- **常驻服务**：**必须用 `connectedDevice` 类型**的前台服务，不能用 `dataSync`——Android 15 起 `dataSync` 有"24 小时内累计 6 小时"的硬上限，到点系统会回调 `onTimeout()`，做不了常驻。`connectedDevice` 没有这个限制，语义上也正好对应"与本局域网设备保持连接"。代价是必须有常驻通知，用户不能静默隐藏。
- **接收落点**：设置页用 `ACTION_OPEN_DOCUMENT_TREE` 选目录，拿到 `takePersistableUriPermission` 持久授权；支持"默认落点 + 每个根目录单独覆盖"。**不自动进相册**，只有用户点"保存到相册"才走 MediaStore。
- **发现**：必须持有 `MulticastLock`（否则 Wi-Fi 驱动直接过滤组播包），并申请 `NEARBY_WIFI_DEVICES`（Android 13+）。
- **落盘**：优先用 `ParcelFileDescriptor` 直接读写（`DocumentFile` 逐文件操作很慢，小文件多时是灾难）。
- **省电**：传输时申请 `PARTIAL_WAKE_LOCK`；平时只用普通 `WifiLock`，`WIFI_MODE_FULL_HIGH_PERF` 只在传输中开——常开高功耗模式会让续航明显变差，用户会直接卸载。
- **分享入口**：注册 `ACTION_SEND_MULTIPLE`，从微信/相册直接"分享到本应用"。

## 六、后台静默常驻可行性评估

### 6.0 结论速览

| 平台 | 能否"静默常驻、随时可收" | 可靠度 | 主要限制 |
|---|---|---|---|
| NAS | **可以，最可靠** | 高 | 无系统级障碍；注意卷挂载顺序 |
| Windows | **可以** | 高 | 睡眠/休眠期间网卡断电，收不到 |
| Android | **准常驻，双层保活** | 中 | 无障碍服务默认托底 + 前台服务（通知删不掉）；厂商省电仍可能杀；被"强行停止"后无法复活 |

一句话：**Windows 和 NAS 可以承诺"随时在线"，Android 只能承诺"只要通知还在，就能收"。** 产品文案不能把三端写成一个承诺。

### 6.1 NAS：最没有悬念

- systemd：`Restart=always`、`RestartSec=3`、`WantedBy=multi-user.target`，进程崩了自动拉起。
- 依赖顺序：`After=network-online.target` 加数据卷对应的 `.mount` 单元，避免卷还没挂上就开始接收。
- 该系统升级会重启服务，需要确认升级后 unit 仍处于 enabled。
- 无 GUI、无休眠、无电池限制，是三者里唯一可以真正"7×24 静默待命"的。

### 6.2 Windows：可行，但要接受两个物理限制

1. **睡眠/休眠**：系统睡下去网卡也断电，任何进程都收不到包。不要用 `SetThreadExecutionState` 阻止睡眠（用户会很反感）。正确做法是唤醒后 3 秒内恢复监听并重新广播；发送端在对方睡眠时应**立即报"对方不可达"**，而不是卡 30 秒超时。
2. **防火墙**：入站端口默认被拦。安装时加规则，别指望用户看懂弹窗。

常驻形态两种，按需要选：

- 托盘 + 任务计划（登录时启动）：简单，单用户家用足够。
- Windows 服务 + 托盘前端：做到"无人登录也能收"，代价是进程拆分和本地 IPC。

### 6.3 Android：能做，但不能吹成"永远在线"

这一端是唯一有政策硬约束的，必须写清楚。

**（1）前台服务类型选错，最多只能跑 6 小时。**
Android 15 起，`dataSync` 和 `mediaProcessing` 两类前台服务在 24 小时内累计只能运行 6 小时，超时后系统回调 `Service.onTimeout()`，应用必须自行停止。用它做"常驻等接收"走不通。
**要选 `connectedDevice`**（清单声明 `FOREGROUND_SERVICE_CONNECTED_DEVICE`），它没有这个时长上限，语义也匹配"与局域网设备保持连接"。

**（2）通知必须常驻。**
Android 不允许真正静默的后台服务。可以做到低打扰（低优先级、不响铃、可折叠），但删不掉。这是产品事实，UI 上要提前说明，别让用户以为是 bug。

**（3）Doze 会掐网络。**
系统长时间静止后会挂起网络访问、忽略 wake lock。需要引导用户把应用加入电池优化白名单（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），并且做一页图文引导，而不是丢一句"请关闭电池优化"。

**（4）厂商 ROM 是最大变量。**
小米/华为/OPPO/vivo 等还有一层"自启动管理 + 后台清理"，标准 API 管不到。做法：

- 首次启动检测厂商，跳到对应自启动设置页（各厂商 Intent 不同，需要维护一张映射表）；
- 提供"自检"入口：让用户从别的设备发一个 1 KB 测试文件，收不到就提示去加白名单；
- **不要用**"1 像素透明窗口""播放无声音频"这类保活黑科技——费电、新系统版本随时失效，而且已经有更稳的系统绑定（无障碍），没必要。

**（5）重启与强停。**

- Android 15 起，`BOOT_COMPLETED` 广播不允许拉起 `dataSync` 等类型的前台服务；`connectedDevice` 不在明令禁止之列，但仍受厂商自启动管理，**不保证**能拉起。
- 用户点了"强行停止"后，系统禁止任何自启，只能手动打开。

**（6）息屏后的 Wi-Fi。**
Wi-Fi 省电会让组播包丢失、TCP 延迟升高。策略：平时持普通 `WifiLock` 保持连接，**常驻态不建立长连接、不发心跳**（省电），电脑端靠"缓存 IP + TCP 探活"找手机；只有传输会话建立后才发 15 秒心跳；只在传输时切到 `WIFI_MODE_FULL_HIGH_PERF`。不要为了"随时能被发现"常开高性能锁。

**（7）保活方案：无障碍服务默认托底、常开（参考李跳跳实测）。**

用户已拍板：不考虑上架合规，无障碍服务作为默认托底、常开；`connectedDevice` 前台服务**同时保留**（Android 要求后台网络服务必须有前台服务，二者不是二选一）。技术要点：

- 无障碍服务无法由 App 自动开启，必须用户在系统设置里手动授权。所以"默认常开"落地为：**首次启动全屏引导，可跳过**；开启后进入双层保活，跳过则只用前台服务。用户之后在系统设置里关掉无障碍时，App 检测到并提示。
- 与李跳跳的关键差异在**省电**：它监听所有事件（`accessibilityEventTypes=0xffffffff`）是因为要干活；我们只需要"进程活着"，所以只监听最少事件（低频事件类型），`notificationTimeout` 调大，把回调频率压到最低，几乎零耗电。
- 无障碍服务只解决"进程不被杀"，不解决 Wi-Fi 省电，`WifiLock` 仍然要。
- 跳过引导时：降级为纯 `connectedDevice` 前台服务，功能不变，只是更容易被系统清理。

**（8）省电设计清单（用户要求"尽量省电"）。**

| 项 | 做法 | 省电原理 |
|---|---|---|
| 无障碍事件 | 只监听最少事件类型，`notificationTimeout` 调大 | 事件回调频率是耗电大头 |
| WifiLock | 平时普通模式，传输时才 `HIGH_PERF` | 高性能锁常开会明显掉电 |
| 组播监听 | 手机常驻时**不持续监听组播**；改为每 5 分钟广播 1 次（3 包），其余时间不持 `MulticastLock`。但**固定 UDP 单播端口 53318 始终监听**（收唤醒包），单播不触发 Wi-Fi 组播唤醒 | 组播接收是 Wi-Fi 被唤醒的主要来源 |
| 发现方式 | 电脑端靠"已配对设备缓存 IP + TCP 探活"直接连，不依赖手机在线广播 | 探活是内核级 connect，几乎零耗电 |
| 心跳 | 无活动连接时不发心跳；有连接时 15 秒 | 常驻时没有连接，不产生流量 |
| 通知 | 低优先级、可折叠；收到投递时响一下 | 避免震动/铃声的额外耗电 |
| 前台服务 | `connectedDevice` 类型 | 系统要求，无法省掉 |

### 6.4 三端都要处理的共同问题

| 问题 | 做法 |
|---|---|
| 网络切换 / IP 变更 | 监听网络变化事件，重新绑定监听、重新广播、清空对端缓存 |
| 端口被占用 | 启动时探测，占用则顺延并写回配置；管理页显示实际端口 |
| 心跳与离线判定 | 仅传输会话内：15 秒 ping、60 秒无响应标记离线；常驻态无长连接，靠"缓存 IP + TCP 探活"判活；发送前先探活 |
| 常驻带来的攻击面 | 默认"仅已配对设备可发起"；陌生人请求只留一条待确认，其余直接拒绝并限速 |
| 休眠/离线体验 | 发送端 2 秒内给出"对方不可达"，不要静默超时 |
| 日志膨胀 | 统一 2 天滚动，单文件上限 10 MB |

### 6.5 降级路径（Android 被杀之后）

1. 发送端探活失败 → 提示"对方可能未运行或被系统清理"，并给一键重试。
2. 接收端下次打开时，自动补收 10 分钟内未完成的会话（发送端任务窗口 10 分钟，过期即失败并明确提示）。
3. **不做"唤醒已被系统冻结的 App"这种承诺**——UDP 唤醒包只能叫醒仍在运行、仅 Wi-Fi 省电的接收端；App 被冻结或强停后，只能由用户手动打开。

### 6.6 手机作为"投递目标"的专门设计

用户明确的核心场景是：**电脑上右键 → 选手机 → 手机上响一下 → 点开就看**，全程不掏手机、不开 App。这和"坐在电脑前互传文件"是两种交互，设计重点不同。

**（1）免确认接收。**
已配对设备发来的文件直接收，不弹"是否接受"。**默认对所有已配对设备生效**，可在设备详情里单独关闭。陌生人发来的仍然要确认。这是"顺手"能成立的前提——如果每次都要在手机上点一下，还不如打开 App。

**（2）唤醒包。**
手机锁屏时前台服务还在，但 Wi-Fi 可能进入省电状态。发送端先发 3 个 **UDP 单播**唤醒包（间隔 300 ms）到手机的 53318 端口，收到应答再建 TCP 连接；没应答就直接连，仍失败则立即报"手机未响应"。接收端只监听这个固定单播端口，**不持 `MulticastLock`**，与省电要求不冲突。注意：唤醒包只能叫醒"仍在运行、只是 Wi-Fi 睡着了"的接收端，叫不醒被系统冻结的 App。

**（3）通知即入口。**
接收完成立刻出通知，点击用系统默认程序打开（`FileProvider` + `ACTION_VIEW`）。图片用大图样式，文本给前几行预览。**收到时响一下 + 通知，不亮屏**（用户已定）。这才叫"在手机上打开"，而不是"在文件管理器里翻到它"。

**（4）落点固定。**
默认落到用户预设目录（如"下载/互传"），不弹选择框。落点可在设置里改，但每收一个文件问一次是不可接受的。

**（5）小文件优先。**
投递场景多是文档、图片、安装包。调度上让 50 MB 以下的文件走优先队列，大文件后台慢慢传，保证"发完三秒就能看"。

**（6）10 分钟窗口的含义。**
任务在发送端保留 10 分钟。手机 10 分钟内没上线就判失败并明确告知，不无限转圈。

**（7）与普通传输的区别。**

| 维度 | 投递模式 | 普通传输 |
|---|---|---|
| 触发方式 | 电脑右键菜单 | 应用内选择文件/文件夹 |
| 接收确认 | 免确认（仅信任设备） | 可配置 |
| 落点 | 固定预设目录 | 每次可选 |
| 文件大小 | **≤ 10 GB** | 不限 |
| 失败处理 | 10 分钟窗口后放弃 | 可手动重试 |

### 6.7 结论

- **NAS：真常驻，7×24 可承诺。**
- **Windows：真常驻（睡眠除外），可承诺"开机即在线"。**
- **Android：准常驻**，无障碍服务默认托底 + `connectedDevice` 前台服务并存，配合电池/自启动白名单引导，只能承诺"通知在，就能收"。
- 常驻本身**不增加传输协议复杂度**，但要在会话层预留"探活 + 待发队列 + 离线补收"，这部分接口必须在 **v0.1（M0，第一版）** 就定下来，不能等 Android 版本再改协议。

## 七、里程碑

不给工期，只排依赖顺序，每步都能独立验收。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0 协议冻结 + 回环 PoC** | 定稿帧格式、manifest、**探活与待发队列接口**；同机两进程互传 10 GB | 本机吞吐接近磁盘上限；哈希一致 |
| **M1 电脑 ↔ NAS** | 发现、配对、目录传输、断点续传、同名策略、**Windows 托盘常驻 + 自动发现 + 右键菜单基础版**、systemd 守护、NAS 管理页基础版 | 千兆 ≥110 MB/s；拔网线 3 次可续传完成；关掉窗口后仍能接收 |
| **M2 加入 Android** | `connectedDevice` 前台服务、SAF 落点设置、**投递模式（免确认 + 通知直接打开 + UDP 唤醒包）**、分享入口、白名单引导页 | Wi-Fi 6 ≥60 MB/s；锁屏 30 分钟后从电脑右键投递，10 秒内手机收到并能点开 |
| **M3 稳定性加固** | 小文件批量优化、超长路径、权限失败、磁盘满、断电恢复、10 分钟任务窗口 | 10 万文件目录不崩；异常全部有明确报错 |
| **M4 体验与性能打磨** | 二维码配对、拖拽、历史、万兆调优、可选 QUIC 备用通道 | 万兆 ≥800 MB/s；CPU ≤1 核 |

### 各阶段共同的验证方式

- 每次改动按"本地回环 → 双机有线 → 手机无线"三档递进验证，低档不过不进高档。
- 传输正确性统一用"块哈希 + 整文件根哈希"双重校验，不靠肉眼看文件大小。
- 性能数据必须记录环境（网卡速率、磁盘类型、CPU），否则数字没有可比性。

## 八、风险与待定问题

| 风险 | 说明 | 应对 |
|---|---|---|
| 小文件性能 | 10 万个 4 KB 文件，元数据和往返开销远大于数据本身 | 清单批量下发 + 数据通道流水线化；M4 考虑把小文件合并成 pack 流 |
| Android 存储碎片化 | 各家 ROM 对 SAF/后台限制不同 | 优先 `ParcelFileDescriptor`；保留"保存到相册"备选路径 |
| 组播被屏蔽 | 企业 AP、访客网络、部分路由器默认隔离 | 三条腿发现；手动 IP 永远可用 |
| 磁盘成为瓶颈 | 机械盘写入可能只有 100 MB/s | 接收端按实际写速拉块（背压），不盲目追求网络跑满 |
| NAS 权限 | 该平台对应用目录属主敏感 | 只写白名单目录，专用用户 + ACL，不碰应用目录 |
| **Android 常驻被系统杀掉** | 厂商省电策略无法完全规避 | 无障碍服务默认托底常开 + `connectedDevice` 前台服务 + 电池白名单引导 + 10 分钟重试窗口；文案不承诺"永远在线" |
| **常驻监听放大攻击面** | 端口长期对外开放 | 仅已配对设备可发起；陌生人请求只留 1 条待确认并限速；NAS 只写目录白名单 |
| **睡眠导致发送失败** | 物理限制，无法绕过 | 探活 2 秒内报"不可达"；唤醒后自动恢复监听与广播 |

**已全部拍板，无待定。** 本轮确认：项目名"通传"、代码目录 `<仓库目录>\`、无障碍引导可跳过且默认托底常开、不亮屏、投递上限 10 GB、右键子菜单。

后续实现中若出现需要产品决策的问题，写入 `通传\待定问题.md` 后跳过继续，不阻塞开发。
