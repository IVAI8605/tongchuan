## 0 结论先行

1. **形态**：Rust workspace（`tc-core` + `tc-jni`）+ 四个外壳（CLI `tc`、Android、Tauri 桌面、飞牛 fpk）。协议、落盘、信任、管理页全在 `tc-core`；外壳都是薄壳（`Cargo.toml:2-17`）。
2. **传输模型**：一条控制连接（长度前缀 + JSON 消息）+ N 条数据连接（20 字节定长帧头 + 8 MiB 块），TLS 1.3 自签证书 + 指纹固定。协议 `0.20` 与包版本解耦（`session.rs:29`、`frame.rs:5-11`）。
3. **一次接收的必经关**：版本门禁 → 块大小门禁 → 信任门禁 → 落点解析 → 路径双闸 → 增量跳过 → 落点占用 → 位图/懒创建 → 逐块 Merkle 校验 → 收尾改名 + mtime（`session.rs:1948-2459`）。
4. **开发闭环本机可跑通（实测）**：`cargo test --workspace --locked` → **167 通过 / 0 失败**，编译 36 秒；`tc --version` 输出 `1.4.0`，未知命令退出码 `2`。
5. **有 4 处文档/代码漂移**，发版前必须处理：README 版本行仍写「Windows/Android/fpk 仍 1.3.1」、`main.rs` 启动日志仍在提示 `manage.token`、`cli/error.rs` 声明了永不出现的退出码 3/4、状态卡 §2 仍写「未 push」。
6. **两个默认值分歧值得拍板**：Windows 桌面端缺省 `hash_cache = true`（核心缺省 `false`）；`tc recv` 不带 `--identity` 时全明文、无信任门禁（排障入口）。

## 3 主链 A：`tc send`（发送端）

触发：`tc send --to <ip:port> --dir <path>...`（`main.rs:798`）

1. `cli::spec::validate` 先做参数/数值校验，用法错误 exit 2（`main.rs:749`）。
2. 未给 `--peer-fp` → 听 2 秒发现广播，取同主机公告的指纹（`main.rs:806-817`、`358-369`）；没听到就退回明文（显式降级）。
3. 有指纹 → `TlsOpener` 并加载本机证书（`main.rs:374-393`）；身份目录与 `tc trust` 同一套解析规则。
4. `build_manifest_with_progress` 扫描目录树、算 BLAKE3 根哈希，扫描阶段也回报进度（`session.rs:1026-1040`）。
5. 控制连接发 `HELLO`（txnId/device/pairCode/protocol version/blockSize/caps）→ 收 `HELLO_ACK`：版本不兼容或块大小不符立刻报错，`BUSY` 直接失败（`session.rs:1043-1071`）。
6. 发 `MANIFEST`（可带 `force`、`destId`）→ 收 `MANIFEST_ACK`（`acceptedFileIds` / `streams`）；跳过文件数 = 清单总数 − 接受数（`session.rs:1073-1092`）。
7. 按接收端要求的流数开 N 条数据连接，每条先发 `DATA_HELLO{txnId,stream}`（`session.rs:1099-1110`）。
8. 0 号流由主线程服务并回报进度，其余流在 `thread::scope` 里并发；任一流失败置 `abort`，收尾按失败处理（`session.rs:1139-1183`）。
9. 发 `DONE`，等 `VERIFY_OK` / `VERIFY_FAIL`；失败文件映射回本机绝对路径（`session.rs:1185-1213`）。
10. `record_send` 写发送历史（成功/失败都写，`main.rs:541-630`）；`--retry` 时按 30s/2m/10m 重试，仅网络类错误可重试（`retry.rs:12, 38`）。

**旁路**：`--queue-dir` 时失败入队（`main.rs:849-873`），`tc flush` 补发；`maybeprobe` 不适用（Android 侧独立实现）。

## 4 主链 B：`tc daemon`（接收端）

触发：`tc daemon --config config.toml`（`main.rs:1175`）

1. `Config::load_or_create` → `DaemonState::new`（内部先 `config.validate()`，`daemon.rs:337`）→ 建落点/日志/队列目录。
2. `TC_LOG_LEVEL` 覆盖日志级别，非法值不静默（`main.rs:1184-1197`）；装 panic hook（时间 + 退出码 + 末 20 行）。
3. 起三个线程：管理页 `web::serve`、UDP 公告 `announce_forever`、发现监听 + 单播回执（`main.rs:1213-1281`）。
4. 构造 `TrustGate`（信任库 + `trust_mode` + 静态配对码 + 二维码令牌），绑 `TcpListener`，组 `ReceiverHub`（gate/streams/hash_cache/destinations 全在这里注入，`main.rs:1325-1401`）。
5. `hub.serve` 每条连接一个线程；`dispatch` 读首包：`HELLO` 建会话、`DATA_HELLO` 把连接投给对应会话、其它回 `BUSY`（`session.rs:2591-2639`）。
6. `handle_session` 顺序硬编码：HELLO → 版本门禁 → 块大小门禁 → 信任门禁（`session.rs:2017`）→ `HELLO_ACK`（带落点清单）→ `DEST` 或 `MANIFEST` → 落点解析 → `plan_layout` 路径双闸 → `already_present` 增量跳过（`session.rs:2111`）→ `PathClaims` 占位（`session.rs:1734`）→ `MANIFEST_ACK` → 建目录/开半成品 → 取数据连接 → 多流收块 → `DONE` → 校验/收尾 → 裁决（`session.rs:1968-2458`）。
7. 每场会话结束必归还会话名额与落点声明，再回调写历史/日志（`session.rs:2691-2702`、`main.rs:1403-1470`）。
8. 连续 20 次 accept 异常才停服（`main.rs:1471-1486`）。

## 5 契约与不变量（改代码前必须知道）

| 项 | 值 / 规则 | 位置 |

| 落点 | 默认 `destination` + 可选 `[[destinations]]`；每个 path 必须在 `allow` 内 | `daemon.rs:157-216` |

| 版本规则 | 三端同号；协议独立；push/Release 需用户明确授权 | `docs/README.md:8-9, 79` |

### 11.3 本次唯一代码改动（仅测试）

`tests/e2e.rs` 的 `discovery_announce_is_received`：公告里的 `port` 由 `53318` 改为 `53399`，并写明原因。

- 机制：监听侧以「发送方 IP + 公告里的 port」为 `addr` 键（`discover.rs:333`），本机桌面守护进程每 3 秒也发一条 `port=53318` 的回环公告，键相同会把本条覆盖 → 用例间歇失败。
- 证据：改动前同一台机连续复跑 3 次 = PASS / FAIL / PASS；改动后连续 6 次 = 6 PASS；随后全门禁 9/9。
- 回滚：`git checkout -- tests/e2e.rs`。
